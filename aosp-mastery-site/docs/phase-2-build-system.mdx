## 1. The build in one picture

AOSP does not use a single build tool. It is three layers:

| Tool | Language | Role |
|------|----------|------|
| **Soong** | **Blueprint** (`.bp`, Go-syntax) | The modern build: describes *what* to build (modules, sources, deps). |
| **Kati** | `Android.mk` (GNU make) | The legacy layer, kept for the parts not yet migrated to Soong. |
| **Ninja** | `build.ninja` | The actual executor: reads a graph and runs the exact commands, fast. |

Soong and Kati both **generate** a Ninja graph; Ninja **runs** it. When you type
`m`, the `envsetup.sh`/`build` wrapper orchestrates all of this.

<WhyItWorked>
This is why AOSP builds are fast on the second run: Ninja tracks every input and
only re-runs commands whose inputs changed. Learning which layer to edit - a
`.bp` (Soong) versus an `.mk` (Kati) - is the core skill of this phase.
</WhyItWorked>

## 2. Set up the environment and choose a target

`lunch` selects a **target**: a product/device and a build variant. The format
is `product_name-release_config-build_variant` (for example
`aosp_cf_x86_64_only_phone-aosp_current-userdebug`).

<TestRunner
  title="Source the environment, then lunch"
  cmd={`cd aosp
source build/envsetup.sh
lunch aosp_cf_x86_64_only_phone-aosp_current-userdebug`}
  expect={`============================================
PLATFORM_VERSION_CODENAME=...
PLATFORM_VERSION=...
TARGET_PRODUCT=aosp_cf_x86_64_only_phone
TARGET_BUILD_VARIANT=userdebug
TARGET_ARCH=x86_64
============================================

(TARGET_PRODUCT and TARGET_BUILD_VARIANT must match what you passed to lunch.)`}
/>

:::warning The `trunk_staging` form is outdated
Older material used lunch strings like `aosp_<name>-trunk_staging-userdebug`.
That release-config is no longer valid; use the `-aosp_current-` form above
(the plan's corrected-command table, section 6.2).
:::

## 3. First build with `m`

`m` (from `envsetup.sh`) builds from the root of the tree. The first build is
the long one. Later builds reuse Ninja's outputs.

<TestRunner
  title="Build the default target (first build)"
  cmd={`m`}
  expect={`...
[  0% 12/...] ...
[  1% 340/...] ...
...
#### build completed successfully (HH:MM:SS) ####

(The first build can take a long time. Subsequent builds are incremental and
finish in minutes or seconds.)`}
/>

:::note The source tree is read-only on Android 17+
Modern AOSP checks the tree out read-only, so a build step that writes into the
tree must be told it may. The documented switch is
`BUILD_BROKEN_SRC_DIR_IS_WRITABLE=true`. You will need this when you edit a
`.bp` and rebuild (section 4). It is expected behaviour, not a broken setup.
:::

## 4. Edit a `.bp` and rebuild incrementally

Blueprint files declare modules. Here is a minimal `cc_library` you can add to
see the build system pick up a new module. Put it somewhere it is referenced,
or read it alongside an existing `.bp` to compare.

```text
// Example: a minimal Soong module (Blueprint / .bp syntax)
cc_library {
    name: "libhello",
    srcs: ["hello.cpp"],
    cflags: ["-Wall", "-Wextra"],
    shared_libs: ["liblog"],
}
```

<DoThis
  steps={[
    'Open an existing Android.bp in the tree and read one module it declares.',
    'Change something small and real: add a source file to an existing module, or add a cflag.',
    'Rebuild with `m` and confirm only the affected targets rebuild.',
    'Revert if you were experimenting; keep the tree clean.',
  ]}
/>

<TestRunner
  title="Incremental rebuild after a .bp edit"
  cmd={`# after editing a .bp (and, on Android 17+, exporting the writable-tree override)
export BUILD_BROKEN_SRC_DIR_IS_WRITABLE=true
m`}
  expect={`...
[ 99% ...] ...
#### build completed successfully (MM:SS) ####

(An incremental build after a small .bp change should be far shorter than the
first build. If it rebuilds everything, your change touched a common input.)`}
/>

<WhyItWorked>
Soong reads your `.bp`, resolves the module graph, and regenerates the relevant
Ninja edges. Because Ninja hashes inputs, only the modules whose inputs you
changed (and their dependents) re-run. That is the payoff of separating
description (Soong) from execution (Ninja).
</WhyItWorked>

## 5. Flash-free boot: run it on Cuttlefish

Cuttlefish is a virtual device - no phone required. Phase 0 installed its host
packages and added you to the `kvm`/`cvdnetwork`/`render` groups (after a
reboot). Boot your freshly built images.

<TestRunner
  title="Launch Cuttlefish from your build output"
  cmd={`# from the tree where you synced (the android-cuttlefish checkout)
HOME=$PWD ./bin/launch_cvd --daemon`}
  expect={`... (Cuttlefish starts its virtual device) ...
(launch_cvd returns once the device is starting. WebRTC UI:
 https://localhost:8443 )`}
/>

Then confirm it is alive with the standard tooling:

<TestRunner
  title="Confirm the device booted"
  cmd={`adb wait-for-device
adb shell getprop sys.boot_completed`}
  expect={`1

(sys.boot_completed = 1 means the device finished booting. If adb is not found,
run it from $ANDROID_HOST_OUT/bin, or add it to PATH.)`}
/>

<WhyItWorked>
Cuttlefish runs the same images Android builds for real hardware, on your
machine. Because you set `TARGET_PRODUCT=aosp_cf_x86_64_only_phone`, the build
produced exactly the images Cuttlefish boots. This is the tightest loop this
course offers: edit, rebuild, reboot - no physical device.
</WhyItWorked>

## 6. Mastery check

Unassisted, complete a **clean build** of the Cuttlefish target and **boot it**.
Concretely, you have:

- Sourced `envsetup.sh` and `lunch aosp_cf_x86_64_only_phone-aosp_current-userdebug` (section 2).
- Run a full `m` that completed successfully (section 3).
- Edited a `.bp` (or an equivalent real module change) and seen an **incremental** rebuild pick it up (section 4).
- Launched Cuttlefish and confirmed `sys.boot_completed = 1` (section 5).

**Spine artifact:** commit your `.bp` instrumentation change and the build/boot
proof under `spine/02-instrumentation` in your Project Spine fork (plan section
4.8). This is the artifact the competency map records for this phase.
