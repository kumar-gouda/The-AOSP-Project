## 1. The Build Architecture: Soong, Kati, and Ninja

A common mistake for beginners is thinking that typing `m` runs a traditional Makefile. In reality, modern AOSP uses a multi-stage compilation pipeline:

```text
       ┌────────────────────────┐         ┌────────────────────────┐
       │   Modern Android.bp    │         │    Legacy Android.mk   │
       │   (Declarative Go/DSL) │         │    (GNU Make syntax)   │
       └───────────┬────────────┘         └───────────┬────────────┘
                   │                                  │
                   ▼                                  ▼
       ┌────────────────────────┐         ┌────────────────────────┐
       │         Soong          │         │          Kati          │
       │  (Evaluates Modules)   │         │ (Translates to Ninja)  │
       └───────────┬────────────┘         └───────────┬────────────┘
                   │                                  │
                   └────────────────┬─────────────────┘
                                    │ Generates
                                    ▼
                         ┌─────────────────────┐
                         │   out/build.ninja   │
                         │ (Exact Command DAG) │
                         └──────────┬──────────┘
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │     Ninja Tool      │
                         │ (Parallel Compiler) │
                         └──────────┬──────────┘
                                    │ Invokes clang / rustc / dx
                                    ▼
                         ┌─────────────────────┐
                         │ system.img / boot   │
                         └─────────────────────┘
```

<DeepDive title="Why Did Android Abandon GNU Make for Soong + Ninja?">
In Android 6.0 and earlier, whole-tree Makefiles took over **15 minutes just to evaluate the build tree** before a single C++ file was compiled!
- **GNU Make is Turing-complete**: Developers wrote complex shell scripts and recursive loops inside `Android.mk`, making builds non-deterministic and impossible to cache reliably.
- **Soong enforces determinism**: `Android.bp` has **no variables, no conditionals, and no functions**. Everything is static data.
- **Ninja is blazing fast**: Ninja doesn't know what C++ or Java is. It only knows inputs, outputs, and shell commands. If an input file hasn't changed its timestamp or hash, Ninja skips it instantly in milliseconds.
</DeepDive>

## 2. Setting Up the Shell and Selecting a Target (lunch)

Before running the build, you must import AOSP's suite of shell helper functions (`lunch`, `m`, `croot`, `godir`) by sourcing `build/envsetup.sh`.

```bash
cd ~/aosp
source build/envsetup.sh
```

Now select your target using `lunch`:

<TestRunner
  title="Select the Cuttlefish x86_64 target"
  cmd={`lunch aosp_cf_x86_64_only_phone-aosp_current-userdebug`}
  expect={`============================================
PLATFORM_VERSION_CODENAME=REL
PLATFORM_VERSION=17
TARGET_PRODUCT=aosp_cf_x86_64_only_phone
TARGET_BUILD_VARIANT=userdebug
TARGET_ARCH=x86_64
TARGET_ARCH_VARIANT=x86_64
HOST_ARCH=x86_64
============================================`}
/>

<DeepDive title="Dissecting the Target String Format">
Modern Android lunch strings follow the strict 3-part syntax:
`product_name-release_config-build_variant`

For example: `aosp_cf_x86_64_only_phone-aosp_current-userdebug`:
1. **`aosp_cf_x86_64_only_phone`**:
   - `aosp_`: Standard open-source tree device configuration.
   - `cf_`: Cuttlefish virtual reference device.
   - `x86_64_only`: Builds purely 64-bit binaries without 32-bit legacy multilib overhead, cutting build time in half!
   - `phone`: Phone profile packages.
2. **`aosp_current`**:
   - The trunk-stable release configuration defining active feature flags (replaces outdated `trunk_staging`).
3. **`userdebug`**:
   - The build variant.
</DeepDive>

## 3. The Full Build with m

Once `lunch` sets the target, type `m` to invoke the build:

```bash
m
```

<TestRunner
  title="Initial whole-tree compilation"
  cmd={`m`}
  expect={`[  0% 12/154210] ...
[  1% 1542/154210] ...
...
[100% 154210/154210] ...
#### build completed successfully (01:42:15) ####`}
/>

:::warning Android 17 Read-Only Source Tree
Android 17+ checks out the source tree as **read-only** to ensure build hermeticity and prevent rogue compiler steps from writing temporary files into the source directory.
If a legacy script or custom tool attempts to write outside `out/`, the build will fail with a permission error.
To allow writes while developing experimental modules, export:
`export BUILD_BROKEN_SRC_DIR_IS_WRITABLE=true`
:::

## 4. Editing an Android.bp Module and Incremental Rebuilds

In AOSP, every directory with code contains an `Android.bp` file describing its modules.

Here is a typical C++ native library module:

```text
// Android.bp
cc_library {
    name: "libspine_sensor",
    vendor_available: true,
    srcs: [
        "SensorManager.cpp",
        "SensorReader.cpp",
    ],
    cflags: [
        "-Wall",
        "-Wextra",
        "-Werror",
    ],
    shared_libs: [
        "libbase",
        "liblog",
        "libcutils",
    ],
    export_include_dirs: ["include"],
}
```

### Fast Module-Only Compilation

Instead of running a full `m` which checks the entire 150,000-target tree, you can compile **only your specific module**:

```bash
# Build only libspine_sensor and its immediate dependencies
m libspine_sensor
```

## 5. Booting Cuttlefish Virtual Device

Once the build finishes, your compiled partition images live in:
`$ANDROID_PRODUCT_OUT` (`out/target/product/vsoc_x86_64/`).

To boot your freshly built system on Cuttlefish:

```bash
launch_cvd --daemon
```

Verify that the device booted successfully:

<TestRunner
  title="Check Cuttlefish boot completion"
  cmd={`adb devices
adb shell getprop sys.boot_completed`}
  expect={`List of devices attached
0.0.0.0:6520	device

1`}
/>

Access the visual interactive screen of your running Cuttlefish Android device by opening your browser to:
**`https://localhost:8443`**
