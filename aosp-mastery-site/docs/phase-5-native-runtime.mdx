## 1. Bionic: Android's libc

Android does not use glibc. It uses **Bionic**, its own C library (BSD-derived,
small, with a stable ABI for the platform). Most libc code you already know
compiles against it, but Bionic makes deliberate trade-offs (it favours a small
footprint and a stable ABI over feature completeness).

<WhyItWorked>
Because the platform talks to one libc (Bionic) with a stable ABI, the framework
and native daemons interoperate without shipping their own libc. Cross-compiling
with the **NDK** targets Bionic, which is why an NDK binary runs on the device
but a glibc binary will not.
</WhyItWorked>

## 2. Track A - a native daemon that starts at boot

The deliverable: a small native program (NDK/C++) that init launches on first
boot, with **no manual step**. You add it as a **Soong module**, declare it as an
`init.rc` service (Phase 3), and confirm it is running after a reboot.

Do this: write a tiny native daemon and wire it into the build and boot.

```cpp
// hello_daemon.cpp - a minimal native daemon
#include <cstdio>
#include <unistd.h>

int main() {
  // A real daemon would install signal handlers and a loop.
  std::printf("hello_daemon: started (pid %d)\n", getpid());
  for (;;) {
    sleep(60);  // stay alive; init keeps long-running services supervised
  }
  return 0;
}
```

A Soong module to build it (Android.bp):

```text
// Android.bp
cc_binary {
    name: "hello_daemon",
    srcs: ["hello_daemon.cpp"],
    cflags: ["-Wall", "-Wextra"],
    shared_libs: ["liblog"],
    init_rc: ["hello_daemon.rc"],
}
```

And the init `.rc` that launches it at boot:

```text
# hello_daemon.rc
service hello_daemon /system/bin/hello_daemon
    class main
    user shell
    group shell
    disabled
on property:sys.boot_completed=1
    start hello_daemon
```

<WhyItWorked>
`init` is PID 1 and supervises services. Because you declared `hello_daemon` and
started it from the `sys.boot_completed` trigger, it comes up on every boot by
the system's own rules - not by a human typing a command. That "runs from first
boot, no manual step" property is exactly what the mastery check asks for.
</WhyItWorked>

## 3. Track B - the Zygote fork model and ART basics

Every Android app process is **forked from Zygote**, a process that pre-loads
the Android runtime and framework classes so a new app starts fast.

```
init -> zygote (preloads ART + framework) -> fork -> app process
```

Do this: watch Zygote fork a child when an app starts.

<TestRunner
  title="Trace a Zygote fork"
  cmd={`adb logcat -b all -d | grep -E "zygote|AndroidRuntime" | tail -n 10`}
  expect={`... zygote64: Late-enabling -Xcheck:jni
... zygote: Forked child process 4567
... AndroidRuntime: ... Process: ... started

(Zygote forks a child for each app; the child then specialises into that app.
The preload is why the fork is cheap.)`}
/>

<WhyItWorked>
Zygote loads **ART** (Android Runtime) and common framework classes **once**,
then **forks**. Copy-on-write means the child shares that preloaded memory until
it writes. ART then runs the app's **DEX** bytecode (AOT-compiled ahead of time,
or JIT at runtime). The expensive setup is paid once, not per app.
</WhyItWorked>

## 4. Trace an APK install

When an APK is installed, the system parses and optimises it. Watch the Package
Manager work.

<TestRunner
  title="Install an APK and watch the log"
  cmd={`adb install -r /path/to/some.apk
adb logcat -b all -d | grep -iE "PackageManager|dexopt|installd" | tail -n 15`}
  expect={`Performing Streamed Install
Success
... PackageManager: ... Package ... installed ...
... installd: ... dexopt ... or ... compiled ...
... PackageManager: ... verif ...

(The manager verifies and records the package; installd and dexopt prepare the
code the runtime will run.)`}
/>

<WhyItWorked>
`adb install` hands the APK to the framework, which records it in the package
database; `installd`/`dexopt` then optimise the DEX for the device's runtime.
This is the install path you will extend (or debug) in later phases when you add
or change platform code.
</WhyItWorked>

## 5. Track C - run one `atest` host test

`atest` is Android's test runner. It finds and runs a test module by name. Run a
small **host** test to see the harness work (Phase 1 built a GTest; this runs one
inside the platform harness).

<TestRunner
  title="Run an atest host test"
  cmd={`source build/envsetup.sh
atest hello_world_test`}
  expect={`... (atest locates and builds the test module) ...
[  PASSED  ] 1 test.
...
(atest builds what the test needs, runs it, and reports pass/fail. Use a small,
fast module while learning.)`}
/>

:::tip Pick a fast, self-contained test
`atest` can build a lot. For a first run, choose a small host test module (the
kind that builds in a minute), so you are learning the harness rather than
waiting on a full target build. `atest --help` lists the options.
:::

## 6. Track D - Rust literacy (read-only, ~3 days)

AOSP now contains Rust (drivers, some services, and tooling). You do **not** need
to *write* Rust this phase - you need to **read** it without being blocked. This
is a deliberate, time-boxed literacy unit.

## 7. Mastery check

The bar is a **native daemon that runs from first boot with no manual step**.
Concretely, you have:

- An NDK/C++ daemon built as a Soong module and launched by an `init.rc` service at boot (section 2).
- Traced a Zygote fork and can explain the fork model and ART basics (section 3).
- Traced an APK install through PackageManager/installd (section 4).
- Run one `atest` host test green (section 5).
- Read a Rust file in the tree without being blocked (section 6).

**Spine artifact:** commit the daemon source, its `Android.bp` and `.rc`, and the
boot proof under `spine/05-ndk-daemon` in your Project Spine fork (plan section
4.8). This is the artifact the competency map records for this phase.
