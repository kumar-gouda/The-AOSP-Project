<DidYouKnow title="Why Android Created Bionic Instead of Using GNU Glibc">
  Why did Android go through the enormous effort of writing a custom C library (Bionic) instead of using the battle-tested GNU <code>glibc</code> like Ubuntu and Debian?
  <br /><br />
  <strong>1. Licensing:</strong> <code>glibc</code> is licensed under the LGPL (Lesser GNU General Public License). Hardware vendors (Qualcomm, Samsung, Sony) shipping proprietary camera tuning blobs, DSP binaries, and GPU drivers feared that linking against an LGPL C library could legally force them to publish proprietary source code. Bionic is licensed under permissive BSD/Apache 2.0.
  <br /><br />
  <strong>2. Lightweight Memory Footprint:</strong> When Android launched on the HTC Dream in 2008, the phone had only 192 MB of RAM. Glibc's static memory tables and locale bloat were too heavy. Bionic was stripped down to the bare essentials.
  <br /><br />
  <strong>3. Linker Namespace Isolation:</strong> Bionic does not just provide <code>malloc</code> and <code>printf</code>; it contains Android's custom dynamic linker (<code>/system/bin/linker64</code>). The Bionic linker partitions system memory into strict <em>linker namespaces</em>, preventing vendor hardware libraries from accidentally or maliciously loading internal Android private frameworks.
</DidYouKnow>

## 1. Bionic: Why Android Built Its Own C Library

If you compile an ordinary Linux program on Ubuntu with GCC and push it to Android via ADB, running it will immediately fail with:
`-sh: ./my_program: not found` or dynamic linker errors.

Why? Because Android does **not use GNU glibc**. It uses **Bionic**.

## 2. Building a Production Native Daemon

A production native daemon in AOSP must:
1. Link against Bionic and `liblog` for structured logging.
2. Handle Unix signals (`SIGTERM`, `SIGINT`) cleanly so `init` can shut it down without data corruption.
3. Be defined as a `cc_binary` in `Android.bp`.
4. Be launched and monitored automatically by an `init.rc` service.

Do this: Create `spine_daemon.cpp`:

```cpp
// spine_daemon.cpp
#include <csignal>
#include <cstdio>
#include <unistd.h>
#include <android/log.h>

#define LOG_TAG "SpineDaemon"
#define ALOGI(...) __android_log_print(ANDROID_LOG_INFO, LOG_TAG, __VA_ARGS__)
#define ALOGE(...) __android_log_print(ANDROID_LOG_ERROR, LOG_TAG, __VA_ARGS__)

static volatile sig_atomic_t g_running = 1;

void handle_signal(int signal) {
  if (signal == SIGTERM || signal == SIGINT) {
    g_running = 0;
  }
}

int main(void) {
  // 1. Install clean shutdown signal handlers
  struct sigaction sa{};
  sa.sa_handler = handle_signal;
  sigaction(SIGTERM, &sa, nullptr);
  sigaction(SIGINT, &sa, nullptr);

  ALOGI("Spine Sensor Daemon starting up (PID: %d)", getpid());

  // 2. Main daemon event loop
  int sample_counter = 0;
  while (g_running) {
    ALOGI("Sensor sample tick #%d", ++sample_counter);
    sleep(10); // Sleep interval (in a real driver, this waits on poll() or ioctl())
  }

  ALOGI("Spine Sensor Daemon received shutdown signal. Exiting cleanly.");
  return 0;
}
```

Now declare the daemon in `Android.bp`:

```text
// Android.bp
cc_binary {
    name: "spine_daemon",
    vendor_available: true,
    srcs: ["spine_daemon.cpp"],
    cflags: [
        "-Wall",
        "-Wextra",
        "-Werror",
    ],
    shared_libs: [
        "liblog",
        "libcutils",
    ],
    init_rc: ["spine_daemon.rc"],
}
```

And define its supervisor script in `spine_daemon.rc`:

```text
# spine_daemon.rc
service spine_daemon /system/bin/spine_daemon
    class main
    user system
    group system input
    disabled

# Automatically trigger the service once boot is verified
on property:sys.boot_completed=1
    start spine_daemon
```

## 3. The Zygote Fork Model and the ART Runtime

Every single user application in Android (Calculator, Settings, YouTube) is **not launched directly by `init`**. Instead, every app is a clone of the **Zygote** daemon.

```text
      ┌─────────────────────────┐
      │       init (PID 1)      │
      └────────────┬────────────┘
                   │ Starts at boot
                   ▼
      ┌─────────────────────────┐
      │   Zygote (PID ~400)     │
      │ ├── Initializes ART VM  │
      │ ├── Pre-loads Classes   │
      │ └── Listens on Socket   │
      └────────────┬────────────┘
                   │
    ActivityManager issues fork command over /dev/socket/zygote
                   │
         ┌─────────┴─────────┐
         ▼                   ▼
┌──────────────────┐ ┌──────────────────┐
│   App Process A  │ │   App Process B  │
│  (Camera App)    │ │  (Settings App)  │
└──────────────────┘ └──────────────────┘
```

<DeepDive title="Step-by-Step Anatomy of an App Launch">
1. When you tap an app icon, **`system_server` (ActivityManagerService)** decides to start the app.
2. `system_server` opens a Unix Domain Socket connection to `/dev/socket/zygote` and sends a command: `spawn package=com.example.app uid=10142 ...`.
3. Zygote calls **`fork()`**. Thanks to Copy-on-Write (COW), this fork completes in **under 5 milliseconds**!
4. The newly forked child process executes specialization:
   - Drops all root/system privileges.
   - Sets its Linux User ID (`setuid(10142)`) and Group ID (`setgid(10142)`).
   - Installs SELinux app domain (`untrusted_app`).
   - Closes the Zygote server socket.
5. The child invokes the Java entry point: `android.app.ActivityThread.main()`.
</DeepDive>

## 4. The DEX Compilation Pipeline: From Java to Machine Code

How does Java/Kotlin code execute on a physical CPU in Android?

```text
 Developer Workstation               Ahead-Of-Time (dex2oat)           Physical CPU Execution
┌─────────────────────┐             ┌────────────────────────┐         ┌─────────────────────┐
│ Java / Kotlin Code  │             │ Target Android Device  │         │ ARM64 / x86_64 CPU  │
└──────────┬──────────┘             └───────────┬────────────┘         └──────────┬──────────┘
           │ javac / kotlinc                    │                                 │
           ▼                                    │                                 │
┌─────────────────────┐                         │                                 │
│ JVM Bytecode (.class│                         │                                 │
└──────────┬──────────┘                         │                                 │
           │ d8 / r8 tool                       │                                 │
           ▼                                    ▼                                 │
┌─────────────────────┐ Compile during idle ┌────────────────────────┐            │
│ DEX Bytecode (.dex) ├────────────────────>│ Native ELF Machine Code├────────────┘
│ (Packed into .apk)  │                     │ (.odex / .oat file)    │
└─────────────────────┘                     └────────────────────────┘
```

- **DEX (Dalvik Executable)**: Register-based bytecode designed to minimize memory usage compared to stack-based JVM bytecode.
- **JIT (Just-In-Time) Compiler**: When an app first runs, ART interprets bytecode and JIT-compiles hot loops into RAM. It logs frequently run methods to a profile file (`/data/misc/profiles/cur/0/<package>/primary.prof`).
- **dex2oat AOT Compiler**: When the phone is plugged into a charger overnight, the `dexopt` background service runs `dex2oat` using the recorded JIT profile, generating highly optimized native assembly code stored in `/data/app/<package>/oat/arm64/base.odex`.

## 6. Rust in AOSP Literacy

Over 70% of historical high-severity security vulnerabilities in Android were **memory safety bugs in C/C++** (buffer overflows, use-after-free, double-free, dangling pointers).

To eliminate this class of vulnerabilities at the root, Google declared **Rust as a first-class systems language in AOSP**. Key subsystems (the Android Bluetooth stack `Gabeldorsche`, Keystore 2.0, UWB, and Virtualization) are now written in Rust.

Here is how a Rust module is declared in `Android.bp`:

```text
// Android.bp
rust_binary {
    name: "spine_rust_daemon",
    crate_name: "spine_rust_daemon",
    srcs: ["src/main.rs"],
    rustlibs: [
        "libandroid_logger",
        "liblog_rust",
        "libnix",
    ],
    prefer_rlib: true,
}
```

And the Rust implementation (`src/main.rs`):

```rust
// src/main.rs
use log::{info, LevelFilter};
use android_logger::Config;

fn main() {
    android_logger::init_once(
        Config::default()
            .with_tag("SpineRustDaemon")
            .with_max_level(LevelFilter::Info),
    );

    info!("Spine Rust Daemon initialized with compile-time memory safety!");
}
```

<DeepDive title="Why Rust Prevents the Bugs You Met in Track B">
In C/C++, you learned that:
- Pointer arithmetic can overshoot buffer boundaries (buffer overflow).
- Freeing memory while another pointer holds the address causes dangling pointer corruption.
- Accessing a variable across two threads without locks causes data races.

In Rust, the **Borrow Checker** validates object ownership, lifetimes, and references at **compile time**. If code could produce a dangling pointer or a data race, **the compiler refuses to generate machine code**!
</DeepDive>

  title="Hands-on Lab: Catch a Signal Handler Deadlock"
  goal="Intentionally observe a classic multithreaded signal deadlock in native userspace and replace it with an async-signal-safe implementation."

#include <stdio.h>
#include <stdlib.h>
#include <signal.h>
#include <unistd.h>

void on_term(int sig) {
    // UNSAFE: malloc inside signal handler!
    void *ptr = malloc(128); 
    printf("Handled signal %d with allocation at %p\\n", sig, ptr);
    free(ptr);
    exit(0);
}

int main() {
    signal(SIGTERM, on_term);
    printf("PID %d running continuous allocations. Send SIGTERM!\\n", getpid());
    while (1) {
        void *p = malloc(1024);
        free(p);
    }
    return 0;
}

Compile and run:
gcc signal_deadlock.c -o signal_deadlock
./signal_deadlock &
# Send SIGTERM repeatedly while the loop holds the malloc lock:
for i in {1..100}; do kill -TERM %1 2>/dev/null; done`}
  expectedError={`PID 21045 running continuous allocations. Send SIGTERM!
[Process freezes, never prints "Handled signal", and hangs indefinitely without exiting]`}
  diagnosis="When the main loop thread called malloc(), Bionic libc locked the internal heap allocator mutex. While holding that mutex, the OS delivered the SIGTERM signal and suspended the thread to run on_term(). When on_term() also called malloc(), it tried to acquire the same mutex that the interrupted thread was already holding. Because the interrupted thread can never resume until the signal handler finishes, the thread deadlocked against itself permanently."

static atomic_bool g_running = 1;

    g_running = 0; // Async-signal-safe!
}

int main() {
    signal(SIGTERM, on_term);
    while (g_running) {
        void *p = malloc(1024);
        free(p);
    }
    printf("Clean exit after safe signal notification.\\n");
    return 0;
}`}
