## Track A - C++17 for AOSP Userspace (~3-4 weeks)

The goal is to build and test a production-grade, memory-safe C++17 library. AOSP avoids manual `malloc`/`free` and raw `new`/`delete` in modern codebases.

### A1. Stack vs. Heap and RAII Memory Ownership

In C++, memory belongs to two primary zones:
1. **The Stack**: Fast, automatic storage. Local variables are placed on the stack. When the enclosing curly braces `{}` end, stack memory is instantly reclaimed by moving the stack pointer.
2. **The Heap**: Dynamic storage allocated at runtime via `new` or `malloc`. Heap allocations persist until explicitly destroyed. Forgetting to destroy them causes memory leaks; destroying them twice causes memory corruption (double free).

<VocabularyHelper word="RAII (Resource Acquisition Is Initialization)" simple="A C++ pattern where you tie the lifetime of a resource (like heap memory or a file) to a stack variable so it is automatically cleaned up when the variable leaves scope." analogy="Like holding a hotel keycard: when you enter the room (variable created), the lights turn on; when you take the card out and leave (variable destroyed), the lights automatically turn off." /> solves this dilemma: wrap the heap allocation inside a lightweight stack-allocated object. When the stack object leaves scope, its destructor runs and frees the heap memory automatically.

Do this: Create a header `owner.h` with a self-managing buffer:

```cpp
// owner.h
#pragma once
#include <cstddef>
#include <memory>
#include <string>
#include <utility>

/**
 * A memory-safe contiguous byte buffer using RAII.
 * Owns its heap memory exclusively via std::unique_ptr.
 */
class Buffer {
 public:
  // Explicit prevents accidental implicit conversion from size_t to Buffer
  explicit Buffer(std::size_t size)
      : size_(size), data_(std::make_unique<char[]>(size)) {}

  // Default destructor automatically calls data_.~unique_ptr(), freeing memory
  ~Buffer() = default;

  // Move constructor: transfers ownership of heap memory from 'other' to 'this'
  Buffer(Buffer&& other) noexcept
      : size_(other.size_), data_(std::move(other.data_)) {
    other.size_ = 0;
  }

  // Move assignment: releases existing buffer and steals 'other'
  Buffer& operator=(Buffer&& other) noexcept {
    if (this != &other) {
      size_ = other.size_;
      data_ = std::move(other.data_);
      other.size_ = 0;
    }
    return *this;
  }

  // Disable copying to enforce strict single ownership
  Buffer(const Buffer&) = delete;
  Buffer& operator=(const Buffer&) = delete;

  // Observers
  [[nodiscard]] std::size_t size() const noexcept { return size_; }
  [[nodiscard]] char* data() noexcept { return data_.get(); }
  [[nodiscard]] const char* data() const noexcept { return data_.get(); }

 private:
  std::size_t size_{0};
  std::unique_ptr<char[]> data_{nullptr};
};
```

<DeepDive title="Why std::move Does Not Actually Move Anything">
Many beginners assume `std::move()` executes a memory transfer or calls `memcpy`. It does not!

In C++17:
- `std::move(x)` is simply a **compile-time type cast**: `static_cast<std::remove_reference_t<decltype(x)>&&>(x)`.
- It converts an **lvalue** (an object with a name and persistent storage) into an **rvalue reference** (a temporary token signaling "this object is about to be discarded").
- The *actual move* is executed by the **Move Constructor** (`Buffer(Buffer&& other)`), which inspects the rvalue token, copies the raw pointer address `data_ = other.data_`, and resets `other.data_ = nullptr`.
- Cost of moving: 2 pointer assignments (~2 CPU cycles). Cost of deep copying: heap allocation + byte copying (~thousands of CPU cycles).
</DeepDive>

### A2. Const-Correctness and Modern Parameter Passing

In systems programming, bugs frequently occur when functions accidentally modify data they were only supposed to inspect. `const` correctness turns human errors into compile-time errors.

Do this: Create a file `util.cpp` demonstrating modern C++ parameter passing:

```cpp
// util.cpp
#include <iostream>
#include <string>
#include <string_view>
#include <optional>
#include "owner.h"

// 1. Reading read-only objects: Pass by const reference (no copy, no mutation)
void inspectBuffer(const Buffer& buf) {
  std::cout << "Buffer size: " << buf.size() << " bytes\n";
  // buf.data()[0] = 'X'; // COMPILE ERROR: cannot mutate through const reference
}

// 2. String inspection: Use std::string_view instead of const std::string&
// string_view is just a pointer and a length (16 bytes). It avoids string allocations!
std::optional<int> parseAsciiInteger(std::string_view str) {
  if (str.empty()) {
    return std::nullopt; // Clear signal: "no value"
  }

  int result = 0;
  for (char ch : str) {
    if (ch < '0' || ch > '9') {
      return std::nullopt; // Invalid character
    }
    result = result * 10 + (ch - '0');
  }
  return result; // Wrapped in std::optional
}
```

<DeepDive title="The Danger of std::string_view: Dangling References">
`std::string_view` does **not own** any memory. It is purely a non-owning window:
```text
[ std::string_view ] 
  ├── ptr* ──────> points to memory owned by someone else!
  └── length: 12
```
If the underlying `std::string` or character array is destroyed, the `string_view` now points to garbage memory (a **dangling pointer**).
**Rule of thumb**: Use `std::string_view` as function input parameters. Never store a `string_view` inside long-lived structs or heap objects unless you guarantee the source outlives it.
</DeepDive>

### A3. Error-as-Return-Value Pattern (Why AOSP Forbids Exceptions)

In Android system daemons and kernel code, **C++ exceptions (`try / catch / throw`) are disabled via the compiler flag `-fno-exceptions`**.

**Why AOSP avoids exceptions:**
1. **Binary Size & Overhead**: Stack unwinding tables (`.eh_frame`) bloat binary size by 15-30%, which is critical on embedded storage.
2. **Predictable Latency**: Exception propagation has unpredictable execution timing.
3. **Cross-Language ABI Seams**: C code, Linux kernel syscalls, and Binder IPC cannot catch C++ exceptions. An uncaught exception across a JNI boundary crashes the entire process.

Instead, AOSP uses **explicit status codes** or **Result types**:

```cpp
// status.h
#pragma once
#include <string>
#include <utility>

enum class StatusCode {
  Ok = 0,
  NotFound = 1,
  PermissionDenied = 2,
  OutOfMemory = 3,
};

template <typename T>
class Result {
 public:
  static Result<T> Success(T value) {
    return Result(StatusCode::Ok, std::move(value), "");
  }

  static Result<T> Error(StatusCode code, std::string message) {
    return Result(code, T{}, std::move(message));
  }

  [[nodiscard]] bool ok() const noexcept { return code_ == StatusCode::Ok; }
  [[nodiscard]] StatusCode code() const noexcept { return code_; }
  [[nodiscard]] const std::string& message() const noexcept { return message_; }
  [[nodiscard]] const T& value() const { return value_; }

 private:
  Result(StatusCode code, T value, std::string message)
      : code_(code), value_(std::move(value)), message_(std::move(message)) {}

  StatusCode code_;
  T value_;
  std::string message_;
};
```

## Track B - Systems-C for Kernel Work (~2-3 weeks)

The Linux kernel does not use C++. It is written in GNU C11 with direct hardware manipulation, manual pointer offsets, and intrusive data structures.

### B1. Pointers, Pointer Arithmetic, and Memory Alignment

In C, pointer arithmetic does not count bytes; it counts **elements of the pointed type**:
- If `int* p = 0x1000`, `p + 1` evaluates to `0x1004` (because `sizeof(int) == 4`).
- If `char* c = 0x1000`, `c + 1` evaluates to `0x1001` (because `sizeof(char) == 1`).

Hardware architectures (ARM64, x86_64) mandate that memory accesses align with data sizes. An unaligned 64-bit access on some hardware generates an instant hardware bus fault.

Do this: Create `alignment_probe.c`:

```c
/* alignment_probe.c */
#include <stdio.h>
#include <stddef.h>

struct Unpadded {
  char a;       /* 1 byte  */
  int b;        /* 4 bytes */
  char c;       /* 1 byte  */
};

struct Optimized {
  int b;        /* 4 bytes */
  char a;       /* 1 byte  */
  char c;       /* 1 byte  */
  /* 2 bytes padding to align struct to 4-byte boundary */
};

int main(void) {
  printf("Size of Unpadded: %zu bytes (compiler added padding!)\n", sizeof(struct Unpadded));
  printf("  offset of a: %zu\n", offsetof(struct Unpadded, a));
  printf("  offset of b: %zu\n", offsetof(struct Unpadded, b));
  printf("  offset of c: %zu\n", offsetof(struct Unpadded, c));

  printf("Size of Optimized: %zu bytes\n", sizeof(struct Optimized));
  return 0;
}
```

### B2. The container_of Macro: Kernel Intrusive Structures

In userspace C++, containers own items: `std::vector<Item>` manages an array of `Item` objects.
In the Linux kernel, **items own the container linkage**. A kernel linked-list node (`struct list_head`) is embedded *inside* your driver structure!

```text
Memory Layout of struct sensor_device:
┌──────────────────────────────────────┐ <── Address of outer struct (0x2000)
│ int sensor_id                        │     offset: 0
├──────────────────────────────────────┤
│ char name[16]                        │     offset: 4
├──────────────────────────────────────┤
│ struct list_head node ───────────────┼ <── Address of member 'node' (0x2014)
│   ├── struct list_head *next         │
│   └── struct list_head *prev         │
└──────────────────────────────────────┘
```

When the kernel list iterator traverses the list, it holds a pointer to `struct list_head node` (`0x2014`). How does it get back to the enclosing `struct sensor_device` at `0x2000`?
By subtracting the compile-time byte offset:
`address_of_sensor_device = address_of_node - offsetof(struct sensor_device, node)`.

Do this: Create `container_of_demo.c`:

```c
/* container_of_demo.c */
#include <stdio.h>
#include <stddef.h>

/**
 * Standard Linux kernel container_of definition:
 * 1. ptr: pointer to the member.
 * 2. type: the type of the outer container struct.
 * 3. member: the name of the member field inside the container.
 */
#define container_of(ptr, type, member) ({                      \
    const typeof( ((type *)0)->member ) *__mptr = (ptr);        \
    (type *)( (char *)__mptr - offsetof(type, member) );})

struct sensor_device {
  int sensor_id;
  char name[16];
  int reading;
};

int main(void) {
  struct sensor_device dev = {
    .sensor_id = 101,
    .name = "gyroscope",
    .reading = 42
  };

  // Imagine a driver callback only gives us a pointer to the 'reading' field:
  int *reading_ptr = &dev.reading;

  // Recover the parent sensor_device:
  struct sensor_device *recovered = container_of(reading_ptr, struct sensor_device, reading);

  printf("Successfully recovered parent struct!\n");
  printf("Sensor ID: %d\n", recovered->sensor_id);
  printf("Name:      %s\n", recovered->name);
  printf("Reading:   %d\n", recovered->reading);

  return 0;
}
```

### B4. Linux Kernel Error Pointers: ERR_PTR, IS_ERR, and PTR_ERR

In userspace, functions that fail return `-1` or `NULL`. But what if a kernel function allocates an object and returns a pointer (e.g. `struct device *`)? If it returns `NULL`, the caller knows it failed, but **cannot tell why** (was it out of memory, device not found, or permission denied?).

The Linux kernel uses an elegant architectural trick:
On 64-bit systems, the uppermost page of virtual memory (`0xFFFFFFFFFFFFF000` to `0xFFFFFFFFFFFFFFFF`) is never a valid kernel data address. The kernel casts negative error codes (`-ENOMEM = -12`, `-EINVAL = -22`) directly into pointer values within this top page!

```c
/* err_ptr_demo.c */
#include <stdio.h>
#include <stdint.h>
#include <stdbool.h>

#define MAX_ERRNO 4095
#define IS_ERR_VALUE(x) ((uintptr_t)(void *)(x) >= (uintptr_t)-MAX_ERRNO)

static inline void *ERR_PTR(long error) {
  return (void *) error;
}

static inline long PTR_ERR(const void *ptr) {
  return (long) ptr;
}

static inline bool IS_ERR(const void *ptr) {
  return IS_ERR_VALUE(ptr);
}

// Simulated kernel driver function
void *open_sensor(int sensor_id) {
  if (sensor_id < 0) {
    return ERR_PTR(-22); // -EINVAL (Invalid argument)
  }
  if (sensor_id == 999) {
    return ERR_PTR(-12); // -ENOMEM (Out of memory)
  }
  static int dummy_dev = 1;
  return &dummy_dev;     // Valid pointer address
}

int main(void) {
  void *res = open_sensor(-5);
  if (IS_ERR(res)) {
    printf("Driver failed with kernel errno: %ld\n", PTR_ERR(res));
  } else {
    printf("Driver initialized successfully at %p\n", res);
  }
  return 0;
}
```

### B5. The ELF Binary Model: Inspecting Headers, Symbols, and Disassembly

Every Linux and Android executable or library is packaged in the **ELF (Executable and Linkable Format)**.

An ELF binary contains distinct sections:
- `.text`: Compiled machine code instructions executed by the CPU.
- `.rodata`: Read-only constants (string literals, static const tables).
- `.data`: Initialized global and static variables.
- `.bss`: Uninitialized global and static variables (zero-initialized at startup, occupies no space on disk).
