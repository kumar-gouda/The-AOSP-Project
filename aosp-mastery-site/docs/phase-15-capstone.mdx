## 1. Thread one feature full-stack

Pick one feature and carry it through the layers it actually needs. The Spine is
not a pile of exercises; it is the evidence that you built a vertical slice.

| Layer | What the capstone might add | Your phase |
|-------|-----------------------------|-----------|
| Kernel | A module/driver the feature needs | 10 / 10.5 |
| HAL | An AIDL HAL + VINTF + VTS | 6 |
| Framework | A SystemService + app-facing AIDL | 7 |
| App | A client that calls it | 7 |
| Security | SELinux policy so it runs under enforcing | 8 |
| Packaging | An APEX if it ships as a module | 13 |

<WhyItWorked>
A full-stack feature is the curriculum's whole point: it proves you can move
between the layers, not just work in one. Where the feature does not need a
layer (most need no kernel change), say so explicitly - knowing *why* a layer is
untouched is part of the answer.
</WhyItWorked>

## 2. Accept it with the CTS/VTS subset

The capstone's acceptance criterion: a **defined CTS/VTS subset** for your
feature passes. This is why Phases 6, 8, and 13 drilled you on VTS, CTS
security, and Tradefed.

## 4. Sign your commits (the integrity layer)

Signed commits are the anti-forgery layer: a reviewer can tell whether the
attributed author actually authored the commit. GitHub shows a **"Verified"**
badge if the signature matches a key on your account. GitHub documents both SSH
and GPG commit signing - follow GitHub's own docs (linked, not restated, so they
cannot rot).

<TestRunner
  title="Sign a commit and verify the badge"
  cmd={`# configure signing (SSH or GPG per GitHub docs)

git commit -S -m "spine: <message>"
git log --show-signature -1`}
  expect={`... Good "git" signature ...
... gpg: Signature made ... 

(Push to your fork; GitHub renders a "Verified" badge when the signature matches
a key on your account.)`}
/>

## 5. Ship the public repo

Your fork is the credential. The plan's layout (section 21.5):

```text
<learner>/aosp-mastery-spine/     # your public fork
├── README.md                     # capstone writeup
├── phases/
│   ├── 00-basecamp/RESULTS.md    # commands run + real output
│   ├── 01-systems/RESULTS.md
│   └── ...                       # one folder per phase
└── (the actual feature code + tests)
```

<WhyItWorked>
Every tier resolves to a public, inspectable artifact: per-phase `RESULTS.md`
files, the patch series, and the README. A reviewer - or any stranger - can
verify the whole thing without a platform account. That is what makes the
credential real rather than decorative.
</WhyItWorked>

## 7. Mastery check

The bar, per the plan (section 21.3): graded **by a reviewer** against the Phase 0
competency doc, on your **public fork**. Concretely, your capstone:

- Builds and boots on your target (section 3).
- Passes the **defined CTS/VTS subset** for the feature (section 2).
- Is documented in a `README.md` that reproduces (section 3).
- Is **full-stack** where the feature requires it (section 1).
- Is **signed** (section 4).
- Is **reproducible** by a stranger (section 5).

:::caution Not self-graded, by rule
Self-grading is an explicitly rejected anti-pattern. No private-database-only
badges, no unverifiable claims, no invented issuers. Your fork is the evidence;
a reviewer issues the grade.
:::

**Spine artifact:** the **whole spine** - the full patch series, the per-phase
`RESULTS.md` files, and the capstone `README.md` - under `spine/15-full` in your
public fork (plan sections 4.8, 21.5). This is the artifact the competency map
records for this phase, and it is the credential itself.
