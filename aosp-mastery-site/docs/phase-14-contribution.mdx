## 1. The AOSP contribution lifecycle

An AOSP change is not a branch you push; it is a **series of patches** reviewed
in **Gerrit**. The lifecycle:

```
edit -> repo upload -> Gerrit review -> (amend, re-upload) -> submit
```

A **change** (one commit) becomes a patch set on Gerrit. Reviewers comment
inline; you amend and re-upload; a reviewer approves (Code-Review +2) and it is
submitted. Etiquette and clarity matter as much as the code.

<WhyItWorked>
Gerrit is a *review* system, not a hosting service: the unit is the patch set,
and the goal is a reviewer being able to say "yes" quickly. Everything in this
phase - commit-message format, small changes, self-review - exists to make that
easy. The workflow is the skill.
</WhyItWorked>

## 2. Format the commit properly

AOSP has a strict commit-message convention. A good message lets a reviewer
understand the change without asking.

```text
<component>: <short summary in imperative mood>

<Longer body explaining WHAT and WHY, wrapped at 72 columns. Say why
the change is needed, not just what it does.>

Test: <how you tested it - atest target, CTS, manual>
Bug: <bug id, if any>
Change-Id: I<40 hex chars>   # added automatically by the commit hook
```

## 3. Upload and the Gerrit conventions

Uploading turns your commit into a patch set for review. Knowing the review
conventions is half the skill.

<TestRunner
  title="Upload a change for review"
  cmd={`# on your feature branch, with a clean commit
repo upload .
# or a specific project:
repo upload path/to/project`}
  expect={`... Upload project <project> ...
... to https://android-review.googlesource.com/ ...
... 1 change uploaded (1 commit) ...
...

(Your commit is now a patch set on Gerrit, awaiting review.)`}
/>

**Gerrit conventions to internalise:**

| Convention | Why it matters |
|------------|----------------|
| One logical change per commit | A reviewer can reason about it; small changes merge fast. |
| Imperative subject | `Fix X`, not `Fixed X` - it reads as an instruction to the tree. |
| `Test:` line | Reviewers must see how you verified it. |
| Reply to every comment | Even "Done"/"Will fix" - reviewers track resolution. |
| Rebase, don't merge | Keeps history linear; resolves with `git rebase`. |
| No unrelated changes | Hidden scope is the #1 reason a patch is rejected. |

## 4. Self-review before you upload

The highest-leverage habit: review your own patch as a stranger would. You will
catch most reviewer comments before they are made.

<DoThis
  steps={[
    'Read the diff as a whole: does every hunk belong to the stated change?',
    'Check the commit message explains WHY, not just WHAT.',
    'Confirm the Test: line is accurate and reproducible.',
    'Run the reviewer checklist (section 6) against your own patch.',
  ]}
/>

## 5. Orient with cs.android.com

Before touching unfamiliar code, **`cs.android.com`** (the AOSP code search) is
your map. Use it to go from symptom to source fast.

<TestRunner
  title="Use code search to orient (on the web)"
  cmd={`# examples of what you search for at cs.android.com:
#  - the symbol you saw in a stack/log ("FooService")
#  - a string from an error message
#  - "file:foo.cpp symbol" to jump to a definition
#  - "def:" / "class:" qualifiers to narrow results`}
  expect={`... (cs.android.com returns files, definitions, and references across
the whole tree, with links to the exact Gerrit review that changed a line) ...

(The last part matters: every line shows its history, so you can see the review
and reviewers behind the code you are changing.)`}
/>

<WhyItWorked>
On a tree this large, finding the code is the first battle. `cs.android.com`
answers "where is this defined / who calls it / what review changed it" without
a local checkout - so you arrive at a change already knowing its context, which
is exactly what a reviewer wants to see.
</WhyItWorked>

## 6. Mastery check

The bar: a patch **passes a real reviewer's checklist**. Run this checklist
against your own Spine patch - a reviewer will run the same one.

- **Scope:** one logical change; no unrelated hunks (section 4).
- **Message:** component-prefixed imperative subject; body explains *why*; wrapped at 72 (section 2).
- **Change-Id:** present, via the hook (section 2).
- **Test:** line is accurate and reproducible (section 2).
- **Conventions:** replied to comments, rebased (not merged), linear history (section 3).
- **Orientation:** the change reflects understanding of surrounding code (section 5).
