## 1. GKI and the KMI, in one breath

Before Android 11-era changes, every device shipped a different kernel fork -
a maintenance nightmare. **GKI** fixes that: **one** Android Common Kernel (ACK)
binary, with a **stable KMI** (Kernel Module Interface), plus **loadable vendor
modules** for device-specific hardware.

| Term | Meaning |
|------|---------|
| **ACK** | Android Common Kernel - the shared upstream-based kernel source. |
| **GKI** | The single, prebuilt kernel image most devices boot. |
| **KMI** | The *stable* set of exported symbols/ABI vendor modules may rely on. |
| **Vendor modules** | Device-specific `.ko` modules, built separately, loaded into GKI. |

<WhyItWorked>
Because the KMI is stable, Google can ship one tested kernel to many devices.
Vendors write modules against that stable interface instead of forking the
kernel. That is why a Pixel kernel is not rebuilt for each Android release: the
Android release changes userspace/framework, while the GKI (with its stable KMI)
stays put across those releases.
</WhyItWorked>

## 2. Get the ACK source

The kernel you build comes from the **ACK** repository via `repo`, separate from
the platform manifest. The current GKI release train is `android17-6.18`
(kernel 6.18) per the GKI release builds page.

<TestRunner
  title="Sync the Android Common Kernel"
  cmd={`mkdir ack && cd ack
repo init -u https://android.googlesource.com/kernel/manifest -b common-android17-6.18
repo sync -j8`}
  expect={`repo initialized in .../ack
(...syncing kernel projects...)
Syncing work tree: 100% ...
Done.

(The branch common-android17-6.18 tracks the 6.18 GKI release train. Confirm the
current train on the GKI release builds page before you start.)`}
/>

:::warning Branches move; verify the train
The exact GKI branch name is versioned and changes over time. `android17-6.18`
matches the plan's verified table, but always confirm the current train on
source.android.com (GKI release builds) and pin deliberately (plan section 12,
refresh policy).
:::

## 3. Build GKI with Kleaf

**Kleaf** is the Bazel-based kernel build system. You build the GKI from the ACK
tree with its documented entry point.

<TestRunner
  title="Build the GKI (Kleaf)"
  cmd={`cd ack
tools/bazel run //common:kernel_aarch64_dist`}
  expect={`... (Bazel starts, analyses, builds targets) ...
Target //common:kernel_aarch64_dist up-to-date:
  bazel-bin/common/kernel_aarch64_dist/image
...
(artifacts land under bazel-bin/.../kernel_aarch64_dist/)

(The first Kleaf build is heavy. Later builds reuse Bazel's cache. The exact
target name follows the Kleaf docs for your tree.)`}
/>

<WhyItWorked>
Kleaf replaces the old build scripts with a reproducible Bazel build. The
`*_dist` target produces the bootable kernel image plus the module set - exactly
what Cuttlefish (or a device) consumes. You built the **unmodified** GKI: the
whole point is that it boots as shipped, without vendor patches.
</WhyItWorked>

## 4. Boot the GKI on Cuttlefish

Rebuild the Cuttlefish images with your kernel (or use the prebuilt GKI the
platform expects) and boot. In practice you either point the platform build at
your kernel artifacts, or run the GKI as-is on the virtual device.

<TestRunner
  title="Boot Cuttlefish and confirm the kernel"
  cmd={`adb shell uname -a
adb shell cat /proc/version`}
  expect={`Linux localhost 6.18.x-android... #1 SMP PREEMPT ...
Linux version 6.18.x-android... (the kernel banner you built)

(uname reports the kernel release; it should match the 6.18 GKI train you built.)`}
/>

## 5. Read the Binder driver: wait/wake

Binder is Android's IPC. In the kernel it lives in the `binder` driver under the
ACK tree (`drivers/android/binder.c`). You are not writing it here - you are
**reading** the wait/wake pattern: a thread that blocks waiting for work, and
the wakeup that hands it a transaction. This is the kernel half of the IPC you
met at the language level in Phase 1.

Do this: locate and read the relevant functions in the driver source.

<TestRunner
  title="Find the Binder wait/wake code in the ACK tree"
  cmd={`cd ack
grep -n "binder_wait_for_work\\|wake_up_interruptible\\|wait_event_interruptible" \\
  common/drivers/android/binder.c | head -n 15`}
  expect={`...binder_wait_for_work(...) ...
...wake_up_interruptible(...) ...
...(the lines where a waiting thread is woken with pending work)...

(A waiting Binder thread sleeps until another process posts a transaction; the
driver wakes it. That sleep/wake is the mechanism underneath every Binder call.)`}
/>

<WhyItWorked>
A Binder call looks synchronous to the caller, but underneath, a worker thread
**waits** on a queue and is **woken** when a transaction arrives. Seeing the
`wait`/`wake_up` pair in `binder.c` connects the high-level "IPC" idea to the
kernel primitive that implements it - the same idea recurs in Phase 6 and 7
(spiral A-4).
</WhyItWorked>
