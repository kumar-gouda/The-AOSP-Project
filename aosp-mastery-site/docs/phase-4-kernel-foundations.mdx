## 1. The GKI and KMI Architectural Revolution

Before Android 12, the Linux kernel ecosystem on Android was fractured:
```text
Upstream Linux (kernel.org)
       │
       ▼
Android Common Kernel (Google adds Android features)
       │
       ▼
SoC Vendor Kernel (Qualcomm / MediaTek forks and adds 1-2 million lines of chip code)
       │
       ▼
Device OEM Kernel (Samsung / Xiaomi forks again and adds board & sensor code)
```
Each device ended up with a proprietary kernel fork that could **never be updated**. If a critical Linux kernel vulnerability was discovered, millions of phones remained unpatched.

Google solved this with **Project GKI**:

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   Generic Kernel Image (GKI)                           │
│     Prebuilt and signed universally by Google (Single kernel image)     │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                       Frozen KMI Symbol Boundary
                                    │
┌───────────────────────────────────┴────────────────────────────────────┐
│                    Vendor Kernel Modules (.ko)                         │
│   Touchscreen.ko │ Camera.ko │ Wi-Fi.ko │ GPU.ko │ Battery.ko          │
└────────────────────────────────────────────────────────────────────────┘
```

<DeepDive title="How the KMI Freeze Works">
In standard desktop Linux, the kernel has **no stable in-tree ABI**: compiling a kernel module with a slightly different GCC compiler version or config flag causes `insmod` to fail with "Invalid module format".

How does Android achieve a stable KMI?
1. Google defines a symbol whitelist (`kmi_symbol_list`). Only functions on this list are accessible to vendor modules.
2. Google tracks every struct layout using `libabigail` to ensure member byte offsets never change.
3. Vendor modules are compiled against this stable interface (`Module.symvers`).
4. Result: Google can release an OTA updating the kernel from version `6.18.2` to `6.18.15` without requiring vendors to recompile their proprietary `.ko` drivers!
</DeepDive>

## 2. Syncing and Building the ACK with Kleaf

The Android Common Kernel source is maintained in its own dedicated manifest repository, independent of the main AOSP platform tree.

Do this: Initialize and sync the ACK tree:

```bash
mkdir -p ~/ack && cd ~/ack
repo init -u https://android.googlesource.com/kernel/manifest -b common-android17-6.18
repo sync -c -j8 --no-clone-bundle
```

Now build the universal GKI image using **Kleaf** (Bazel):

<WhyItWorked>
Notice what Kleaf built:
- `Image`: The uncompressed binary kernel image that Cuttlefish or device bootloaders execute.
- `vmlinux`: The unstripped ELF binary containing full debug symbols (used for debugging kernel panics).
- `System.map`: Symbol table mapping kernel function names to virtual memory addresses.
</WhyItWorked>

## 3. Booting the Custom GKI on Cuttlefish

You can boot your freshly compiled kernel directly on Cuttlefish by passing the `--kernel_path` flag:

```bash
launch_cvd --kernel_path=$HOME/ack/bazel-bin/common/kernel_aarch64_dist/Image --daemon
```

## 4. Deep Dive: Inside the Binder Kernel Driver (binder.c)

Binder is Android's primary Inter-Process Communication system. While it presents a high-level object-oriented interface to apps, its core engine is a Linux character device driver: `/dev/binder`.

### The Single-Copy Mechanism Explained

How does Binder achieve single-copy transfer?

```text
Process A (Client)                    Linux Kernel (binder.c)               Process B (Server)
┌─────────────────────────┐           ┌────────────────────────┐           ┌─────────────────────────┐
│ Payload Data in Heap    │           │                        │           │ Service Worker Thread   │
│ "GetSensorReading"      │           │                        │           │                         │
├─────────────────────────┤           ├────────────────────────┤           ├─────────────────────────┤
│ ioctl(BINDER_WRITE_READ)│──────────>│ binder_transaction()   │           │ Mapped Receive Buffer   │
└─────────────────────────┘           │                        │           │ /dev/binder mmap(128KB) │
                                      │   copy_from_user()     │           │                         │
                                      │   Copies bytes         │──────────>│ [ Payload Data Lands    │
                                      │   directly into        │           │   Here Directly! ]      │
                                      │   Process B's buffer!  │           └─────────────────────────┘
                                      └────────────────────────┘
```

1. When Process B (the server) starts up, it opens `/dev/binder` and calls `mmap(NULL, 128*1024, ...)`.
2. This creates a shared memory region between Process B's user space and the kernel.
3. When Process A sends an IPC call, the kernel allocates a chunk inside Process B's receive buffer and runs **one single `copy_from_user()`** from Process A's memory straight into Process B's memory.
4. Process B wakes up and processes the data in-place without copying!

### The Wait/Wake Queue in binder.c

Open `drivers/android/binder.c` in your ACK checkout and look at `binder_thread_read`:

```c
// Simplified excerpt from drivers/android/binder.c
static int binder_thread_read(struct binder_proc *proc,
                              struct binder_thread *thread,
                              binder_uintptr_t binder_buffer, ...)
{
    // If no work is queued for this thread, put it to sleep:
    wait_event_interruptible(thread->wait, binder_has_work(thread, do_proc_work));

    // When awakened by an incoming transaction from client:
    struct binder_transaction *t = list_first_entry(&thread->todo, ...);
    
    // Package data header and return to userspace
    put_user(BR_TRANSACTION, (uint32_t __user *)ptr);
    ...
}
```

When no IPC requests exist, server threads sleep on a Linux **wait queue** (`thread->wait`) consuming 0% CPU. When a client calls `ioctl(BINDER_WRITE_READ)`, the kernel places work on the server thread's `todo` list and calls `wake_up_interruptible()`.
