## 1. Treble: why HALs look the way they do

Before Project **Treble**, the Android framework and the vendor hardware code
were tangled; a framework update meant a vendor update. Treble split them with a
**stable interface** (originally HIDL, now **AIDL**) and the **VINTF** (Vendor
Interface) mechanism that declares which interfaces exist and match.

| Concept | Role |
|---------|------|
| **HAL** | A service that exposes a hardware capability behind a stable interface. |
| **AIDL** | The interface definition language used for modern HALs (and framework IPC). |
| **VINTF** | The manifests that declare which HAL interfaces a vendor and framework provide/require, and whether they match. |
| **VTS** | Vendor Test Suite - tests that a HAL honours its declared interface. |

<WhyItWorked>
The stable interface is the contract. The framework calls the AIDL interface; it
does not care how the vendor implements it. VINTF records the contract so the
system can refuse to boot a mismatched vendor/framework pair, and VTS checks the
implementation actually behaves. This is the same stability idea as the GKI's
KMI (Phase 4), applied to hardware interfaces.
</WhyItWorked>

## 2. Define the AIDL interface

An AIDL HAL starts with an `.aidl` file that declares the interface. Here is a
minimal one - a single method returning a value from your daemon's domain.

```text
// IFoo.aidl - minimal HAL interface
package android.hardware.foo;

@VintfStability
interface IFoo {
    // Returns a value computed by the HAL implementation.
    int getVersion();
    // A trivial callable method that returns a string.
    String hello();
}
```

<WhyItWorked>
`@VintfStability` marks the interface as a stable VINTF interface - the promise
that it will not change incompatibly. That annotation is what lets the framework
and vendor agree on the ABI. A HAL is just an AIDL interface plus an
implementation and a manifest entry.
</WhyItWorked>

## 3. Implement the HAL and register it

Write the implementation in C++ (or Rust, later), build it as a service, and
**register it with the service manager** on startup. The service manager is the
name registry every process uses to find Binder services.

## 4. Call it from a native client

A native client finds the service by name through the service manager, gets a
Binder proxy, and calls the method. This is the end-to-end path the mastery
check asks for.

<TestRunner
  title="Native client call"
  cmd={`adb shell foo_client`}
  expect={`hello from IFoo, version=1

(The client resolved android.hardware.foo.IFoo/default via the service manager,
got a proxy, and called hello() over Binder - a cross-process call.)`}
/>

<WhyItWorked>
The call crosses a process boundary, but the AIDL proxy makes it look like a
local method. Under the hood, Binder marshals the arguments, the kernel driver
delivers them to the HAL process, and the result travels back. You saw the
kernel half of this in Phase 4 (`binder.c` wait/wake).
</WhyItWorked>

## 6. Write a VTS test for your own HAL

The testing requirement for this phase: a **VTS test** that calls your HAL and
asserts a correct result. VTS tests live under `test/vts-testcase/hal/` and use
the same GTest-style harness you have used since Phase 1.

```cpp
// A minimal VTS-style test of your HAL.
#include <gtest/gtest.h>
#include "android/hardware/foo/IFoo.h"

using android::hardware::foo::IFoo;

TEST(FooHalTest, HelloReturnsValue) {
  auto foo = IFoo::getService();
  ASSERT_NE(foo, nullptr) << "HAL not registered";
  // AIDL call; adapt to your generated proxy API.
  EXPECT_EQ(foo->getVersion(), 1);
}
```

<TestRunner
  title="Run your VTS test"
  cmd={`atest FooHalTest`}
  expect={`... (atest builds and runs the HAL test on the device) ...
[  PASSED  ] 1 test.
...
(atest runs the VTS test against your running HAL. Green here is the phase's
testing bar.)`}
/>

<WhyItWorked>
A VTS test is not a unit test of your C++ helpers - it is a test **across the
interface**: it finds the registered HAL and calls it exactly as the framework
would. If it passes, your HAL is genuinely callable, not just internally
correct. That is why VTS, not unit tests alone, is the bar for this phase.
</WhyItWorked>

## 7. Mastery check

The bar is a **HAL callable end-to-end, returning a correct value, with a
passing VTS test**. Concretely, you have:

- Defined an AIDL interface and a VINTF-stable HAL (sections 2-3).
- Registered it with the service manager and confirmed it in `service list` (section 3).
- Called it from a native client across the Binder boundary (section 4).
- Traced the Binder transactions (section 5).
- Written and passed a **VTS test** for your HAL (section 6).

**Spine artifact:** commit the `.aidl`, the HAL implementation, its VINTF
manifest, and the VTS test under `spine/06-aidl-hal` in your Project Spine fork
(plan section 4.8). This is the artifact the competency map records for this
phase.
