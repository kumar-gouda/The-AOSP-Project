## 1. The four walls of Android security

Android layers its defences. You have already met most of them without naming
them; this phase names them and makes one real.

| Mechanism | What it enforces |
|-----------|------------------|
| **Permissions** | Which app/UID may call which API (the mediation you met in Phase 7). |
| **SELinux** | Mandatory access control: even root is confined by policy. |
| **Keystore** | Hardware-backed key storage and cryptographic operations. |
| **Verified Boot** | Refuses to boot a system whose images do not match the signed chain. |

<WhyItWorked>
Defence in depth: a bug in one wall does not breach the system. SELinux is the
one you will touch, because every new service must have a policy or the enforcing
build will deny it at runtime - which is exactly the first symptom you will see.
</WhyItWorked>

## 2. SELinux: contexts and policy

SELinux labels every process, file, and socket with a **context** (e.g.
`u:r:foo_service:s0`). **Policy** says which contexts may do what to which
others. A new service needs:

- A **domain** (the process context, e.g. `foo_service`).
- **Type rules** allowing it to do its job (open its files, talk to its HAL).
- A **file context** so its binary and data are labelled correctly.

A minimal policy file looks like this:

```text
# foo_service.te - a minimal SELinux policy for your service
type foo_service, domain;
type foo_service_exec, exec_type, vendor_file_type, file_type;

# Allow init to start the service.
init_daemon_domain(foo_service)

# Allow the service to use the binder it needs, and read its own files.
allow foo_service foo_service:file { read open };
allow foo_service hal_foo_hwservice:hwservice_manager find;
```

<DoThis
  steps={[
    'Add a domain and a file context for your service (foo_service.te, file_contexts).',
    'Start with enforcement off (permissive) and exercise your service.',
    'Read the avc denials from logcat/dmesg.',
    'Add only the allow rules you actually need; re-enable enforcing.',
  ]}
/>

<WhyItWorked>
SELinux policy is deny-by-default: anything you did not explicitly allow is
blocked. So you do not guess the policy from a manual - you **let the denials
tell you** what is missing. That is why the workflow is "run in permissive,
read the denials, add minimal rules, enforce".
</WhyItWorked>

## 3. Resolve a real audit denial

This is the heart of the phase: cause a denial, read it, fix it properly.

<TestRunner
  title="Observe an AVC denial"
  cmd={`adb shell dmesg | grep -i avc | tail -n 10
adb logcat -b all -d | grep -i "avc: denied" | tail -n 10`}
  expect={`... avc: denied { read } for pid=... comm="foo_service" \
    name="..." dev="..." ino=... scontext=u:r:foo_service:s0 \
    tcontext=u:object_r:some_type:s0 tclass=file ...

(The scontext is your service; the tcontext is what it was not allowed to touch;
tclass names the kind of object. That single line tells you the exact rule to
add.)`}
/>

<TestRunner
  title="Turn a denial into a suggested rule"
  cmd={`# from a tree with the build environment sourced
adb shell dmesg > foo.log
cat foo.log | grep "avc: denied" | audit2allow`}
  expect={`#============= foo_service ==============
allow foo_service some_type:file read;

(Treat audit2allow as a suggestion, not gospel: add the narrowest rule that
makes the denial go away. Never run audit2allow -M and ship it blindly.)`}
/>

## 4. Add the CTS SELinux test components

The phase's testing requirement: the **CTS SELinux test components**. CTS
(Compatibility Test Suite) includes tests that assert the device's SELinux
posture - that it is enforcing, that key domains exist, and that policy is not
weakened.

<TestRunner
  title="Run the SELinux CTS test module"
  cmd={`# after building/installing the CTS SELinux test components
atest CtsSecurityHostTestCases -m`}
  expect={`... (atest builds and runs the CTS security host tests) ...
[  PASSED  ] ...
...
(The CTS SELinux components assert the device enforces SELinux and matches the
expected policy shape - a stronger bar than "it booted".)`}
/>

<WhyItWorked>
A service that "boots" is not enough; it must run **under enforcing** and the
platform's security tests must still pass. The CTS SELinux components encode
"production is still locked down" as an automated check - which is exactly the
mastery bar: the service runs cleanly under enforcing.
</WhyItWorked>

## 5. The rest of the wall: Keystore and Verified Boot

You will not rebuild these this phase, but you must be able to place them.

- **Keystore** stores keys in hardware-backed secure storage and performs
  crypto where the key never leaves the secure environment. An app asks Keystore
  to sign/decrypt; the key itself is not extractable.
- **Verified Boot** establishes a chain of trust: the bootloader verifies the
  boot image, which verifies the system. A tampered image breaks the chain and
  the device refuses to boot (or boots with a warning, depending on state).

<Checkpoint
  quiz={{

## Break It

<BreakIt
  items={[
    'Symptom: the service crashes or misbehaves only on an enforcing build, but works in permissive. Cause: a missing allow rule that permissive logs instead of blocking. Fix: read the avc denials it produces and add the narrowest rules.',
    'Symptom: audit2allow suggests a very broad rule (e.g. to an unconfined or su domain). Cause: audit2allow is a heuristic. Fix: narrow it by hand; grant only the specific tclass/permission you need.',
    'Symptom: the CTS SELinux components fail after your change. Cause: you weakened policy to make your service work. Fix: revert the weakening and add precise rules instead - the CTS test exists to catch exactly this.',
  ]}
/>

## 6. Mastery check

The bar is: the **service runs cleanly under SELinux enforcing**. Concretely,
you have:

- Policy and contexts for your Phase 7 service (section 2).
- Resolved at least one **real audit denial** by reading it and adding a minimal rule (section 3).
- Added and run the **CTS SELinux test components** (section 4).
- A clear explanation of permissions, Keystore, and Verified Boot (sections 1, 5).

**Spine artifact:** commit the `.te` policy, the file contexts, and the resolved
`avc` denial (with the log excerpt) under `spine/08-selinux` in your Project
Spine fork (plan section 4.8). This is the artifact the competency map records
for this phase.
