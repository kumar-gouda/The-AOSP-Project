## 3. SELinux Anatomy: Decoding the Context

Every process and file in Android carries a security context. Let's dissect the 4-field tuple:

```
  u     :     r     :       vendor_foo       :   s0
[user]     [role]             [type]           [MLS Level]
```

<DeepDive title="Anatomy of the 4 SELinux Context Fields">
1. **User (`u`):** In Android, there is only one user identity: `u`. Android does not use multiple SELinux users.
2. **Role (`r` or `object_r`):** 
   - Processes (active subjects) run in role `r`.
   - Files, sockets, device nodes, and directories (passive objects) carry role `object_r`.
3. **Type / Domain (`vendor_foo`):** 
   - This is the **most important field** in Android. 
   - When applied to a process, it is called a **domain**.
   - When applied to a file or device node, it is called a **type**.
   - Type enforcement rules govern which domains can perform actions on which types.
4. **MLS Level (`s0`):** 
   - Multi-Level Security / Multi-Category Security. 
   - In system daemons, it is simply `s0`.
   - For Android third-party apps, AOSP uses categories (e.g., `s0:c512,c768`) to mathematically isolate different apps from each other, even when they share the same generic `untrusted_app` domain.
</DeepDive>

## 4. Writing SELinux Policy for Your Service

To allow your Phase 6 HAL (`vendor.foo-service`) to execute and register with `servicemanager`, author policy files under `device/<oem>/<device>/sepolicy/vendor/`:

### 1. Type Declaration: `vendor_foo.te`

<CodeAnnotator
  title="vendor_foo.te: Custom Daemon Domain and Access Rules"
  code={`# Declare the process domain and its executable file type
type vendor_foo, domain;
type vendor_foo_exec, exec_type, vendor_file_type, file_type;

# Associate domain transition: when init executes vendor_foo_exec, transition to vendor_foo domain
init_daemon_domain(vendor_foo)

# Allow the daemon to use Binder IPC
binder_use(vendor_foo)

# Allow the daemon to serve Binder transactions
binder_service(vendor_foo)

# Allow the daemon to register its AIDL interface with servicemanager
add_service(vendor_foo, hal_foo_service)

### 2. File Context Mapping: `file_contexts`

Attach the context to the filesystem path in `device/<oem>/<device>/sepolicy/vendor/file_contexts`:

```text
# Label the daemon binary in /vendor/bin/hw
/vendor/bin/hw/vendor\.foo-service   u:object_r:vendor_foo_exec:s0

# Label any device nodes created by the driver
/dev/foo_device                      u:object_r:foo_device:s0
```

### 3. Service Context Mapping: `service_contexts`

Declare the AIDL service string label in `service_contexts`:

```text
android.hardware.foo.IFoo/default    u:object_r:hal_foo_service:s0
```

## 5. Resolving Real AVC Denials

When SELinux blocks an operation in **Enforcing** mode, the operation fails with `EACCES` (Permission Denied). In **Permissive** mode, the kernel permits the operation but emits an audit log.

### Anatomy of an AVC Denied Log

Let's dissect a real denial line from `dmesg`:

```text
type=1400 audit(1727401234.567:42): avc: denied { read open } for pid=1420 comm="vendor.foo-serv" name="foo_node" dev="sysfs" ino=8412 scontext=u:r:vendor_foo:s0 tcontext=u:object_r:sysfs:s0 tclass=file permissive=0
```

<DeepDive title="Breaking Down the AVC Denial Tokens">
- `avc: denied { read open }`: The requested operations that were blocked.
- `comm="vendor.foo-serv"`: The executable name of the process that made the system call.
- `scontext=u:r:vendor_foo:s0`: **Source Context** (Subject). The domain of the process trying to perform the action.
- `tcontext=u:object_r:sysfs:s0`: **Target Context** (Object). The current label of the file/node being accessed.
- `tclass=file`: **Target Class**. The kind of kernel object (e.g., `file`, `dir`, `chr_file`, `binder`, `service_manager`).
- `permissive=0`: `0` indicates SELinux was in Enforcing mode (action was blocked). `1` indicates Permissive mode (action was logged but allowed).
</DeepDive>

### Why Blindly Running `audit2allow` is Dangerous

If you feed the denial above into `audit2allow`:

```bash
cat denial.txt | audit2allow
```

It will suggest:

```text
# DANGEROUS FIX PROPOSED BY AUDIT2ALLOW:
allow vendor_foo sysfs:file { read open };
```

<WhyItWorked>
**DO NOT DO THIS!** 
`sysfs` is a generic, top-level type applied to thousands of hardware registers. Granting your daemon `read` access to all of `sysfs` violates AOSP CTS `neverallow` rules and creates a major security hole.

**The Proper Engineering Fix:**
1. Do not broaden the allow rule.
2. **Re-label the target object** with a specific type!
3. Create a dedicated type: `type sysfs_foo, sysfs_type, fs_type;`
4. Label `/sys/devices/platform/foo/foo_node` as `u:object_r:sysfs_foo:s0` in `genfs_contexts` or `file_contexts`.
5. Grant the narrow rule: `allow vendor_foo sysfs_foo:file { read open };`
</WhyItWorked>

## 7. Android Verified Boot (AVB 2.0)

SELinux protects userspace at runtime, but what protects SELinux policy files on disk from offline tampering? That is the job of **Android Verified Boot (AVB)**.

```
+-----------------------------------------------------------+
|               Hardware Root of Trust (ROM)                |
|  Verifies Bootloader (aboot/abl) RSA Public Key           |
+-----------------------------+-----------------------------+
                              |
                              v
+-----------------------------------------------------------+
|              Bootloader & vbmeta Partition                |
|  Verifies Kernel boot.img & dm-verity Hash Trees          |
+-----------------------------+-----------------------------+
                              |
                              v
+-----------------------------------------------------------+
|                 Linux Kernel & dm-verity                  |
|  Cryptographically authenticates every 4KB block read     |
|  from /system, /vendor, and /product partitions           |
+-----------------------------------------------------------+
```

<WhyItWorked>
`dm-verity` uses a Merkle hash tree stored at the end of each partition image. When the kernel reads a filesystem block, it hashes the 4KB block and verifies it against the hash tree up to the root hash stored in `vbmeta`. If an attacker mounts the flash storage on a computer and modifies `vendor_foo.te` or `/system/bin/sh`, the hash check fails immediately with `EIO`, halting the corrupted read.
</WhyItWorked>
