## 1. Rust in AOSP

Rust is a first-class language in AOSP, with official documentation and build
support. You learned to *read* it in Phase 5; here you *build* with it. AOSP
supports several Rust module types:

| Module type | Android.bp rule | Use |
|-------------|-----------------|-----|
| **Library** | `rust_library` | Shared logic, linked by others. |
| **Binary** | `rust_binary` | An executable. |
| **Test** | `rust_test` | Unit tests. |
| **Fuzzer** | `rust_fuzz` | Coverage-guided fuzzing. |

```text
// Android.bp - a Rust library with a test
rust_library {
    name: "libspine_rust",
    crate_name: "spine_rust",
    srcs: ["src/lib.rs"],
}

rust_test {
    name: "libspine_rust_test",
    crate_name: "spine_rust_test",
    srcs: ["tests/test.rs"],
    rustlibs: ["libspine_rust"],
}
```

<WhyItWorked>
Rust's memory safety is why AOSP is adopting it for new code - fewer classes of
bug make it to production. But it is still *AOSP code*: it builds with Soong,
is tested with your existing harness, and lives in the same tree. Phase 5 taught
you to read it; this makes you able to ship it.
</WhyItWorked>

## 2. A minimal APEX

An **APEX** (Android Pony Express) is a package that ships a system component as
an updatable module - the basis of **Mainline**, where parts of the OS update
independently of a full OTA. Packaging the Spine as an APEX is a production
step.

```text
// Android.bp - a minimal APEX
apex {
    name: "com.android.spine",
    manifest: "apex_manifest.json",
    binaries: ["spine_daemon"],
    // For an updatable module, also declare it in the build and sign it.
}

// apex_manifest.json
{
  "name": "com.android.spine",
  "version": 1
}
```

## 3. Graphics and Camera HAL overview

You will not write a graphics or camera HAL here, but you must be able to place
them - your capstone may touch one.

- **Graphics:** `SurfaceFlinger` (compositor), the **HWC** (Hardware Composer
  HAL), and `gralloc` (buffer allocation HAL). Apps draw into buffers;
  SurfaceFlinger composes them via the HWC.
- **Camera:** a layered HAL (camera provider, device, and the app-facing
  `CameraService`), with camera HALs built on the provider model. It is one of
  the most vendor-specific parts of a device.

<WhyItWorked>
Both are "find the seam" subsystems: the framework side (SurfaceFlinger,
CameraService) is AOSP; the hardware side (HWC, gralloc, camera provider) is
vendor. Knowing where that seam is tells you whether a change is yours to make
in AOSP or something a vendor must provide - the key production question.
</WhyItWorked>

## 4. Trade Federation and host-driven tests

You have used `atest` throughout. Under it is **Trade Federation (Tradefed)**, a
host-driven test harness that orchestrates tests across one or many devices. A
**host-driven test module** runs on the host and drives the device - useful when
the test logic is complex or spans devices.

```text
// Android.bp - a host-driven test module (shape)
android_test {
    name: "SpineHostDrivenTest",
    srcs: ["src/**/*.java"],
    // Tradefed orchestrates: install, run on device, collect results.
}
```

<TestRunner
  title="Run a host-driven test module"
  cmd={`atest SpineHostDrivenTest`}
  expect={`... (Trade Fed builds, installs, and runs the module on the device) ...
[  PASSED  ] 1 test. ...
...

(atest delegates to Trade Fed, which drives the device and returns results -
this is the testing path the phase records.)`}
/>

<WhyItWorked>
Tradefed is the harness behind `atest`, CTS, and VTS: it handles device setup,
installation, execution, and result collection at scale. Writing a host-driven
module means your test can orchestrate the device rather than run inside it -
the pattern production tests use.
</WhyItWorked>

## 5. Name every subsystem: the production question

The mastery bar is a **reasoning** one: given your capstone feature, name every
subsystem it touches in a real ship. Use the full stack you have built:

| Layer | Ask yourself |
|-------|--------------|
| Kernel | Does it need a module/driver change (Phase 10/10.5)? |
| HAL | A new or changed AIDL HAL, with VINTF + VTS (Phase 6)? |
| Framework | A SystemService + app-facing AIDL (Phase 7)? |
| Security | SELinux policy, permissions (Phase 8)? |
| Packaging | An APEX/Mainline module (section 2)? |
| Testing | Unit / CTS / VTS / Tradefed coverage (this phase)? |
| Real device | Partition/slot implications (Phase 11-12)? |
