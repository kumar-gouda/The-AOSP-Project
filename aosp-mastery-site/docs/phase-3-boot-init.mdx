<DidYouKnow title="Why Android Uses a Two-Stage Init (First-Stage vs Second-Stage)">
  In traditional Linux desktop distributions, the kernel mounts the root filesystem directly from the storage disk using <code>root=/dev/sda1</code>.
  <br /><br />
  <strong>Why That Fails on Modern Android:</strong> Starting in Android 10, Android introduced <strong>Dynamic Partitions</strong>. The physical partition is just one large blob called <code>super</code>. Inside <code>super</code>, partitions like <code>system</code>, <code>vendor</code>, and <code>product</code> are dynamically resized and encrypted, requiring cryptographic verification with <code>dm-verity</code>. Even worse, the flash storage drivers (UFS or eMMC) might be loadable kernel modules (<code>.ko</code>) that are not compiled into the monolithic kernel!
  <br /><br />
  <strong>The Two-Stage Solution:</strong>
  <ol>
    <li><strong>First-Stage Init (in RAM):</strong> The kernel extracts a tiny ramdisk into RAM and runs <code>/system/bin/init</code> in first-stage mode. This stage loads kernel modules, reads device tree overlays, sets up device-mapper dm-verity nodes, and mounts the real <code>/system</code> filesystem.</li>
    <li><strong>Second-Stage Init (on /system):</strong> Init performs a <code>switch_root</code> into the newly mounted filesystem, re-executes itself, loads SELinux policy, and starts the core user daemons.</li>
  </ol>
</DidYouKnow>

## 1. The Complete Boot Sequence

From power button press to interactive home screen, the handoff passes through 6 distinct stages:

```text
 1. Boot ROM (PBL)        Burned into hardware SoC; verifies and loads XBL/ABL bootloader.
        │
        ▼
 2. Bootloader (ABL)      Initializes DDR RAM, verifies boot.img cryptographic signature (AVB).
        │
        ▼
 3. Linux Kernel          start_kernel() runs, sets up MMU, interrupts, device drivers, mounts ramdisk.
        │
        ▼
 4. init (PID 1)          Mounts partitions, enforces SELinux, parses init.rc, spawns daemons.
        │
        ▼
 5. Zygote Daemon         Initializes ART VM, pre-loads 5,000+ classes, forks system_server.
        │
        ▼
 6. system_server         Starts 80+ SystemServices; launches Launcher (Home Screen) app!
```

<DeepDive title="First-Stage vs. Second-Stage Init (PID 1)">
Why does `init` execute in two separate stages?
1. **First-Stage Init (Ramdisk / init_boot partition)**:
   - When the kernel boots, physical storage partitions like `/system` and `/vendor` are **not mounted yet**.
   - The kernel unpacks a minimal in-memory ramdisk and executes `/init` (First-stage).
   - First-stage `init` mounts virtual filesystems (`/dev`, `/proc`, `/sys`), initializes `dm-verity` storage encryption, mounts dynamic partitions (`/system`, `/vendor`), loads required early kernel modules, and initializes SELinux.
   - Once the real `/system` partition is mounted, first-stage init calls `execv("/system/bin/init", ...)` to transition seamlessly into **Second-stage Init**!
2. **Second-Stage Init (/system/bin/init)**:
   - Sets up the **Property Service**, establishes signal handlers to reap child processes, parses `/system/etc/init/hw/init.rc` and vendor `.rc` files, and starts native services like `servicemanager`.
</DeepDive>

## 2. Inspecting Early Boot: dmesg

The kernel writes its boot logs to a fixed-size circular ring buffer in kernel memory (`/dev/kmsg`). You read it using `dmesg`.

<TestRunner
  title="Read kernel early boot logs"
  cmd={`adb shell dmesg | head -n 25`}
  expect={`[    0.000000] Linux version 6.18... (android17-6.18-...)
[    0.000000] Command line: ... console=ttyS0 ...
[    0.000000] Memory: ...K/...K available
[    0.000000] ...
[    1.240112] Run /init as init process
[    1.245890] init: init first stage started!
[    1.450123] init: Loading SELinux policy...`}
/>

<WhyItWorked>
Notice the timestamp format `[    0.000000]`: these are seconds and microseconds elapsed since hardware reset.
Near timestamp ~1.2s, the kernel completes hardware initialization and executes `/init`. Userspace has officially begun.
</WhyItWorked>

## 4. The Android Init Language: Actions and Services

The behavior of `init` is defined by `.rc` files located in:
- `/system/etc/init/`: Platform services.
- `/vendor/etc/init/`: Hardware vendor HAL services.
- `/system/etc/init/hw/init.rc`: Primary boot script.

An `.rc` file consists of two primary constructs:
1. **Actions (`on <trigger>`)**: Sequences of commands executed when an event occurs.
2. **Services (`service <name> <path> [args]`)**: Programs executed and supervised by init.

```text
# /vendor/etc/init/spine_sensor.rc

# 1. Action: Runs when the boot property triggers
on property:sys.boot_completed=1
    setprop persist.vendor.spine.status "active"
    write /dev/kmsg "Spine Sensor Service: Boot phase verified!"

# 2. Service: Managed daemon process
service spine_sensor /vendor/bin/spine_sensor_daemon
    class main
    user system
    group system input
    capabilities NET_ADMIN
    oneshot
```

## 5. Android System Properties: getprop and setprop

Android's Property Service is a shared memory dictionary of string pairs: `key=value`.

<DeepDive title="Property Naming Rules and Restrictions">
System property names have strictly enforced prefix rules:
- **`ro.*` (Read-Only)**: Set once during boot (e.g. `ro.product.model`). Once set, **cannot be modified** until reboot.
- **`persist.*` (Persistent)**: When changed via `setprop`, init automatically writes the value to `/data/property/`. The value survives device reboots!
- **`sys.*` (System Global)**: Runtime platform status (e.g. `sys.boot_completed`).
- **`vendor.*` (Vendor Partition)**: Properties owned by hardware vendor daemons.

SELinux strictly mediates which processes are allowed to call `setprop` on specific property names via `property_contexts`.
</DeepDive>

Do this: Query and set a custom property:

<TestRunner
  title="Interact with the Property Service"
  cmd={`adb shell setprop persist.vendor.demo.active 1
adb shell getprop persist.vendor.demo.active`}
  expect={`1`}
/>
