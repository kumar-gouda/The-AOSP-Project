## 1. Userspace vs. kernel: the memory model in one picture

A process sees a flat virtual address space. The kernel maps pages behind it.
The boundary is crossed only via **syscalls**. Everything in this phase - fork,
exec, shared memory - is a way of crossing that boundary.

Do this: print the virtual layout facts your process can see.

```c
/* layout.c */
#include <stdio.h>
#include <unistd.h>

int global_init = 42;          /* .data  */
int global_zero;               /* .bss   */

int main(void) {
  int local = 7;               /* stack  */
  printf("pid      = %d\n", getpid());
  printf("&global_init = %p (data)\n", (void *)&global_init);
  printf("&global_zero = %p (bss)\n",  (void *)&global_zero);
  printf("&local       = %p (stack)\n", (void *)&local);
  return 0;
}
```

  title="Build and run it"
  cmd={`gcc -std=c11 -Wall -Wextra layout.c -o layout && ./layout`}
  expect={`pid      = 12345
&global_init = 0x55... (data)
&global_zero = 0x55... (bss)
&local       = 0x7ff... (stack)

(Exact addresses vary per run; the data/bss addresses sit below the stack.)`}

## 2. fork + exec: creating processes

`fork()` clones the calling process; `exec*()` replaces its image. Together
they are how every shell command, and much of Android's `init`, starts work.

Do this: fork a child, have it `exec` a program, and have the parent wait.

```c
/* forker.c */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
  pid_t pid = fork();
  if (pid < 0) { perror("fork"); return 1; }

  if (pid == 0) {
    /* child: replace this image with /bin/echo */
    execl("/bin/echo", "echo", "hello from the child", (char *)NULL);
    perror("execl");      /* only reached if execl fails */
    _exit(127);
  }

  /* parent: wait for the child */
  int status = 0;
  waitpid(pid, &status, 0);
  printf("parent: child %d exited with %d\n", pid, WEXITSTATUS(status));
  return 0;
}
```

<TestRunner
  title="Build and run it"
  cmd={`gcc -std=c11 -Wall -Wextra forker.c -o forker && ./forker`}
  expect={`hello from the child
parent: child 12346 exited with 0

(The child's echo output may interleave with the parent's line.)`}
/>

<WhyItWorked>
`fork()` returns **twice**: `0` in the child, the child's PID in the parent,
and `-1` on failure. That return value is the branch. `execl` does not return on
success - it replaces the process image - so any code after it runs only on
failure. This two-call pattern (fork then exec) is the foundation of process
creation on Linux and the reason Android's `init` can spawn and supervise
services.
</WhyItWorked>

## 3. IPC: shared-memory producer / consumer

Processes are isolated by default. To share data you ask the kernel for a shared
mapping with `mmap(MAP_SHARED)`. (This is the same idea behind Android's
`ashmem`/`memfd` and the buffers Binder passes between processes.)

Do this: one process writes to shared memory, another reads it.

```c
/* shm_producer.c */
#include <stdio.h>
#include <string.h>
#include <sys/mman.h>
#include <fcntl.h>
#include <unistd.h>

int main(void) {
  const char *name = "/aosp_shm_demo";
  int fd = shm_open(name, O_CREAT | O_RDWR, 0600);
  if (fd < 0) { perror("shm_open"); return 1; }
  ftruncate(fd, 4096);

  char *p = mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
  if (p == MAP_FAILED) { perror("mmap"); return 1; }

  strcpy(p, "payload written by the producer");
  printf("producer wrote: %s\n", p);
  return 0;
}
```

```c
/* shm_consumer.c */
#include <stdio.h>
#include <sys/mman.h>
#include <fcntl.h>
#include <unistd.h>

int main(void) {
  const char *name = "/aosp_shm_demo";
  int fd = shm_open(name, O_RDONLY, 0600);
  if (fd < 0) { perror("shm_open"); return 1; }

  char *p = mmap(NULL, 4096, PROT_READ, MAP_SHARED, fd, 0);
  if (p == MAP_FAILED) { perror("mmap"); return 1; }

  printf("consumer read: %s\n", p);
  return 0;
}
```

<TestRunner
  title="Build, produce, then consume"
  cmd={`gcc -std=c11 shm_producer.c -o shm_producer -lrt
gcc -std=c11 shm_consumer.c -o shm_consumer -lrt
./shm_producer
./shm_consumer`}
  expect={`producer wrote: payload written by the producer
consumer read: payload written by the producer`}
/>

<WhyItWorked>
`shm_open` creates a named object in the kernel; `mmap` maps it into the
process. `MAP_SHARED` means writes are visible to other mappings of the same
object - that is the sharing. The two programs never talk directly; the kernel
mediates, which is why this survives the producer exiting before the consumer
runs.
</WhyItWorked>

:::note Cleaning up the shared object
The producer uses `O_CREAT` but never `shm_unlink`, so the object at
`/dev/shm/aosp_shm_demo` persists between runs (a fresh run overwrites it, but
it is still leaked). In real code you unlink after opening - the mapping keeps
working - so the object disappears when the last mapper exits. Add
`shm_unlink(name);` after `mmap` in the producer to see that. This matters in
AOSP too: leaked shared-memory objects are a real resource-leak class.
:::

## 4. Cross-compilation to aarch64

Android devices are mostly `arm64`. You compile on your `x86_64` host for the
target. This is the same mechanism the AOSP build uses under the hood.

<TestRunner
  title="Build for aarch64 and run it under QEMU"
  cmd={`sudo apt-get install -y gcc-aarch64-linux-gnu qemu-user
aarch64-linux-gnu-gcc layout.c -o layout_arm64
file layout_arm64
qemu-aarch64 ./layout_arm64`}
  expect={`layout_arm64: ELF 64-bit LSB pie executable, ARM aarch64, ...

pid      = 12345
&global_init = 0x... (data)
&global_zero = 0x... (bss)
&local       = 0x... (stack)

(Addresses differ from the host build. Running is via QEMU on x86_64.)`}
/>

<WhyItWorked>
`aarch64-linux-gnu-gcc` is a cross-compiler: same source, different target ISA
and ABI. The result is an ELF binary for ARM64, which your x86_64 kernel cannot
run natively - hence `qemu-aarch64` to execute it. In a real AOSP build, this
cross-compilation is driven by the build system rather than called by hand.
</WhyItWorked>

## 5. See it with strace

`strace` shows every syscall a program makes - the actual crossings into the
kernel. This is how you debug "it does not do what I think" at the systems level.

<TestRunner
  title="Trace the forker"
  cmd={`strace -f -e trace=clone,execve,wait4 ./forker 2>&1 | head -n 20`}

  expect={`clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|...) = 12346
execve("/bin/echo", ["echo", "hello from the child"], ...) = 0
...
wait4(12346, ...) = 12346
...
parent: child 12346 exited with 0


(Exact counts differ; you should see clone, then execve, then wait4.)`}
/>

<BreakIt
  items={[

    'Symptom: the consumer reads an empty string or garbage. Cause: you mapped the shared object MAP_PRIVATE (copy-on-write) or never ftruncate()d it to a size. Fix: use MAP_SHARED and ftruncate to a real size before mapping.',

## 6. Mastery check

Ship a multi-process, cross-compiled program, verified with **real `strace`**
output. Concretely, you have:

- A parent that forks a child which `exec`s another program (section 2).
- A shared-memory producer/consumer pair (section 3).
- At least one unit test that runs green (section 3, Testing Thread).
- A build for **both** `x86_64` and `aarch64` (section 4).
- `strace` output showing `clone` -> `execve` -> `wait4` (section 5).
