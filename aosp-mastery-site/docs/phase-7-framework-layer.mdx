## 1. system_server: where platform services live

`system_server` is the Java process that hosts the platform's core services
(ActivityManager, PackageManager, and hundreds more). A **SystemService** is a
class registered here so the rest of the system - and apps - can find it.

```
init -> zygote -> system_server -> { ActivityManagerService, ... your service }
```

<WhyItWorked>
Apps cannot talk to your kernel or HAL directly. The pattern is always: a
SystemService in `system_server` wraps the lower layer and exposes a **safe,
permissioned** API. That indirection is deliberate - it is where permissions,
policy, and lifecycle live. This phase completes the vertical slice: kernel →
HAL → framework → app.
</WhyItWorked>

## 2. Write the SystemService

A SystemService is a class that extends the framework's service base and is
registered with the `ServiceManager`. Here is the shape of a minimal one.

```java
// FooService.java - a minimal SystemService
public class FooService extends SystemService {
    public FooService(Context context) {
        super(context);
    }

    @Override
    public void onStart() {
        // Publish so other processes can find it by name.
        publishBinderService(Context.FOO_SERVICE, new FooImpl());
    }

    private final class FooImpl extends IFoo.Stub {
        @Override
        public int getVersion() {
            return 1;
        }
    }
}
```

<WhyItWorked>
`publishBinderService` registers your stub with the service manager under a
name. `system_server` runs as a privileged process, so it can hold the
permissions your app-facing API requires - and apps then reach it through the
normal Binder path you already understand from Phase 6.
</WhyItWorked>

## 3. Expose app-facing AIDL

The interface your app calls is a **framework AIDL** - the same language as the
HAL, but installed in a framework package and reachable by apps through the
manager.

```text
// IFoo.aidl - framework-visible, app-facing
package android.framework;

interface IFoo {
    int getVersion();
}
```

## 4. Call it from an app

From an app, get the service via the manager and call it. This closes the
vertical slice: the value originated in your kernel/HAL work in Phases 4–6.

<TestRunner
  title="Call the service from an app"
  cmd={`adb shell am start -n com.example.foodemo/.MainActivity
adb logcat -d | grep FooDemo | tail -n 5`}
  expect={`... FooDemo: version from service = 1
...

(The app resolved the SystemService, called getVersion() over Binder, and got
the value your HAL produced - end to end.)`}
/>

<WhyItWorked>
The app only knows the AIDL interface and the service name. Underneath: app →
Binder → `system_server` (permission check) → your service → HAL → kernel. Every
layer you built in Phases 4-6 is now behind one ordinary-looking API call.
</WhyItWorked>

## 5. Add a system-side unit test

The phase's testing requirement: a **system-side unit test** run with `atest`.
Framework services often split logic into a **core** class (plain Java, unit
testable) separate from the Android-dependent shell - the same reason Phase 1
kept logic out of `main`.

```java
// FooServiceCoreTest.java - a system-side unit test
@RunWith(JUnit4.class)
public class FooServiceCoreTest {
    @Test
    public void versionIsStable() {
        FooServiceCore core = new FooServiceCore();
        assertEquals(1, core.getVersion());
    }
}
```

<TestRunner
  title="Run the system-side test"
  cmd={`atest FooServiceCoreTest`}
  expect={`... (atest builds and runs the framework test module) ...
[  PASSED  ] 1 test.
...
(atest runs a system-side unit test on the framework module. Green here is the
phase's testing bar.)`}
/>

<WhyItWorked>
By keeping the *logic* in a plain-Java core class, you unit-test it fast without
a device or `system_server`. The Binder service is then a thin shell around
tested logic. This is the same separation-of-concerns you have practised since
Phase 1, now inside the framework.
</WhyItWorked>

## 6. Mastery check

The bar is that **kernel/HAL work is callable as a normal Android API from an
app**. Concretely, you have:

- A SystemService registered in `system_server` and visible in `service list` (section 2).
- An **app-facing AIDL** interface (section 3).
- A successful call **from an app**, returning your value (section 4).
- A **system-side unit test** run green with `atest` (section 5).

**Spine artifact:** commit the service, its AIDL, the registration diff, the
app, and the unit test under `spine/07-systemservice` in your Project Spine fork
(plan section 4.8). This is the artifact the competency map records for this
phase.
