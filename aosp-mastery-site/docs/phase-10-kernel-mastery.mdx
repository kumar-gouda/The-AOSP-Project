## 1. A module is the atom of kernel code

A kernel module is code the kernel loads at runtime, with the same privileges as
the kernel itself. Once you can write, build, insert, and remove one, the whole
kernel becomes approachable - it is just modules plus core.

<WhyItWorked>
The kernel is not a black box; it is code you can extend. A module has an
`init` (runs on load) and an `exit` (runs on unload), and it talks to userspace
through well-defined interfaces - the simplest being `/proc`. Phases 4-9 gave
you everything above the module boundary; this phase crosses it.
</WhyItWorked>

## 2. Write a minimal module

Start with the atom: a module that logs on load and unload. Then add a `/proc`
entry that userspace can read - the "userspace-observable effect" the mastery
check needs.

```c
// hello_kmod.c - a minimal module with a /proc entry
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/proc_fs.h>
#include <linux/seq_file.h>

static int hello_show(struct seq_file *m, void *v) {
    seq_printf(m, "hello_kmod: version %d\n", 1);
    return 0;
}

static int hello_open(struct inode *inode, struct file *file) {
    return single_open(file, hello_show, NULL);
}

static const struct proc_ops hello_proc_ops = {
    .proc_open = hello_open,
    .proc_read = seq_read,
    .proc_lseek = seq_lseek,
    .proc_release = single_release,
};

static int __init hello_init(void) {
    proc_create("hello_kmod", 0, NULL, &hello_proc_ops);
    pr_info("hello_kmod: loaded\n");
    return 0;
}

static void __exit hello_exit(void) {
    remove_proc_entry("hello_kmod", NULL);
    pr_info("hello_kmod: unloaded\n");
}

module_init(hello_init);
module_exit(hello_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Minimal /proc module for the Project Spine");
```

<TestRunner
  title="Load the module and read its /proc entry"
  cmd={`adb shell insmod /data/local/tmp/hello_kmod.ko
adb shell cat /proc/hello_kmod
adb shell dmesg | grep hello_kmod | tail -n 5`}
  expect={`hello_kmod: version 1
... hello_kmod: loaded ...

(You inserted code into a running kernel, and userspace can now read it through
/proc. That is the userspace-observable effect.)`}
/>

<WhyItWorked>
`proc_create` registers a file in `/proc` backed by your kernel functions; when
userspace reads it, the kernel calls your `hello_show`. `pr_info` writes to the
kernel log (`dmesg`). So the same module is observable from **userspace**
(`/proc`) and **kernel space** (dmesg) - exactly the two views you will use to
diagnose it.
</WhyItWorked>

## 3. Diagnose with kernel tools alone

The phase's core skill: when the module misbehaves, find it with `dmesg` and
`ftrace` - not a userspace debugger. The kernel log is the kernel's own evidence.

<TestRunner
  title="Read the kernel log"
  cmd={`adb shell dmesg | grep -iE "hello_kmod|BUG|WARN|Oops" | tail -n 20`}
  expect={`... hello_kmod: loaded ...
... (or on a bug) BUG: ... or WARNING: ... at ... hello_show+0x...
...

(dmesg carries module messages and kernel WARN/BUG reports, with the faulting
function named inline.)`}
/>

<TestRunner
  title="Trace module function calls with ftrace"
  cmd={`adb shell "echo function > /sys/kernel/tracing/current_tracer"
adb shell "echo hello_show > /sys/kernel/tracing/set_ftrace_filter"
adb shell "echo 1 > /sys/kernel/tracing/tracing_on"
adb shell cat /proc/hello_kmod
adb shell "echo 0 > /sys/kernel/tracing/tracing_on"
adb shell cat /sys/kernel/tracing/trace | head -n 10`}
  expect={`... hello_show ...
...

(ftrace shows your module's functions running in order as userspace triggers
them - proof you are observing kernel behaviour, not guessing.)`}
/>

<WhyItWorked>
`dmesg` tells you *what happened* (and what faulted); `ftrace` tells you *what
ran*. Together they let you reconstruct the kernel's behaviour from its own
records - the only evidence available on a device you cannot attach a debugger
to, which is the point of the mastery bar.
</WhyItWorked>

## 4. The road ahead: kselftest and KUnit

Phase 10 gets you a module and its `/proc` effect. The **testing** thread for
kernel code is **kselftest** (userspace-driven kernel self-tests) and **KUnit**
(in-kernel unit tests). Phase 10.5 goes deeper - a full driver with a
device-tree binding, covered by these tests. For now, know that kernel code is
tested *inside the kernel build*, not with the userspace harnesses you used
earlier.

## 5. Mastery check

The bar: a module produces a **userspace-observable effect, diagnosed with
kernel tools alone**. Concretely, you have:

- Written and built a kernel module into the GKI (section 2).
- Exposed a **`/proc` entry** readable from userspace (section 2).
- Produced the effect and observed it via `/proc` and `dmesg` (section 2).
- Diagnosed a kernel issue using **`dmesg` and `ftrace`** (section 3).
- Placed kselftest/KUnit in the kernel testing landscape (section 4).

**Spine artifact:** commit the module source, its build target, and the
`/proc`/`dmesg` evidence under `spine/10-kmod` in your Project Spine fork (plan
section 4.8). This is the artifact the competency map records for this phase.
