## 1. Cuttlefish vs. a real Pixel

Everything you built so far ran on Cuttlefish - a virtual device. A real Pixel
is the same architecture with real hardware attached. The differences explain
what you can and cannot learn on each.

| Aspect | Cuttlefish | Real Pixel |
|--------|------------|------------|
| Backing | Virtual (crosvm/QEMU) | Physical SoC |
| HALs | Generic/reference, open | Vendor-signed blobs (radio, GPU, camera, DSP) |
| Boot chain | Virtual, no real bootloader | Real bootloader + fastboot, Verified Boot |
| GPU | Software / virtio-gpu | Proprietary driver |
| Radio | None | Real modem (`radio.img`) |
| Setup | Free, minutes | Own the device, unlock, flash |
| Risk | None | Possible bootloop if mis-flashed |
| Best for | Framework/service/kernel-logic | Camera/radio/sensors/power/thermal |

<WhyItWorked>
The architecture you learned is identical; the *implementation* differs. On
Cuttlefish the vendor layer is open and generic, so you can iterate freely. On a
Pixel the vendor layer is signed blobs and the boot chain is real - which is
exactly why you develop framework and kernel logic on Cuttlefish first, and only
touch a physical device when the problem is genuinely hardware (camera, radio,
thermals).
</WhyItWorked>

## 2. The partition and image set

A real device ships a set of **images**, each written to a **partition**. Knowing
which image holds what is the core of this phase.

:::caution Verify per cycle
Partition layout can change between hardware generations. The table below
reflects a GKI-era Pixel image set; **confirm each row against a current factory
image bundle before relying on it**. (This is the plan's `[VERIFY per cycle]`
flag made local to this page.)
:::

| Image | Holds |
|-------|-------|
| `boot.img` | Generic kernel + boot ramdisk (GKI kernel) |
| `init_boot.img` | Generic ramdisk (split since GKI 2.0) |
| `vendor_boot.img` | Vendor ramdisk pieces (paired with generic boot) |
| `vendor_kernel_boot.img` | Vendor kernel modules / DTB (GKI devices) |
| `dtbo.img` / `dtb.img` | Device Tree Blob (Overlay) |
| `vbmeta*.img` | Verified Boot metadata/signatures per group |
| `super.img` | Dynamic container: system, vendor, product, system_ext, vendor_dlkm, system_dlkm |
| `userdata.img` | User data - wiped on unlock |
| `radio.img` | Modem/baseband |
| `bootloader.img` | Bootloader |
| `pvmfw.img` | Protected VM firmware (Android virtualization) |

## 3. A/B slots and what "wrong slot" breaks

Modern devices keep **two copies** of the bootable partitions (slot A and slot B).
An update writes the inactive slot and switches to it on reboot - so a failed
update can fall back. This is why "which slot" matters: an image flashed to the
wrong slot, or a slot that does not match its `vbmeta`, does not boot.

<TestRunner
  title="Inspect slots and the active slot (read-only, on any device)"
  cmd={`# on a device you own (read-only commands)
fastboot getvar current-slot
fastboot getvar slot-count
# and in a running system:
adb shell getprop ro.boot.slot_suffix
adb shell ls -l /dev/block/by-name/ | grep _a
adb shell ls -l /dev/block/by-name/ | grep _b`}
  expect={`current-slot: a
slot-count: 2
...
ro.boot.slot_suffix=_a
...
... boot_a -> ...
... boot_b -> ...

(The device keeps boot_a/boot_b, system_a/system_b, etc. The active slot is
reported by current-slot / ro.boot.slot_suffix.)`}
/>

  steps={[

    'Identify which partitions are slotted (_a/_b) and which are not (e.g. super, userdata).',
    'For one slotted image, write down what breaks if it is written to the wrong slot.',

/>

<WhyItWorked>
Slots exist so that a failed update is recoverable. But that safety depends on
consistency: the bootloader boots the *active* slot, and Verified Boot checks the
`vbmeta` for that slot. Flash the boot image to slot B while the device boots
slot A, and nothing changes; mismatch a slot's image and its vbmeta, and Verified
Boot refuses it - a bootloop unless you can re-flash.
</WhyItWorked>

## 4. The two meanings of "device tree"

The phrase is overloaded, and confusing the two costs hours:

- **Kernel DT** (`.dts`/`.dtsi` → `dtbo`/`dtb.img`): the hardware description
  compiled for the kernel (you met this in Phase 10.5).
- **Community slang** (`device/<vendor>/<codename>/`): the device-specific AOSP
  *source directory* a `lunch` target builds.

<Checkpoint
  quiz={{
    question: 'A guide says "find the device tree for your Pixel." Which meaning does it usually intend?',
    options: [
      'The compiled dtbo.img in the factory image.',
      'The device-specific AOSP source directory (device/<vendor>/<codename>/).',
      'The kernel log.',
      'The vbmeta signature.',
    ],
    answer: 1,
    explain:
      'In community/AOSP bring-up slang, "the device tree" is the source directory under device/<vendor>/<codename>/. The kernel DT is the .dts/.dtsi compiled to dtbo/dtb.img. Same words, different things.',
  }}
/>

## Break It

<BreakIt
  items={[
    'Symptom: a freshly flashed image does not boot and the device loops. Cause: an image was written to a slot whose vbmeta does not match it, so Verified Boot refuses. Fix: flash a consistent set to the active slot (or reflash the factory image).',
    'Symptom: you flash boot.img to the inactive slot and nothing changes. Cause: the active slot did not change. Fix: this is expected - to test it you must switch the active slot (as an update would).',
    'Symptom: you cannot flash at all ("not allowed in locked state"). Cause: the bootloader is locked. Fix: fastboot flashing unlock wipes the device first - use a secondary/used device, never your daily driver.',
  ]}
/>
