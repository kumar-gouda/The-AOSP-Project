<DidYouKnow title="Why Android Created A/B Slots (The End of Bricked Devices)">
  In early Android (Android 1.0 to 6.0), applying a system update was terrifying.
  <br /><br />
  <strong>The Death of Recovery Flashing:</strong> An update required rebooting the entire phone into a special recovery OS (<code>recovery.img</code>). The recovery program wiped the active <code>/system</code> partition block-by-block and extracted the new OS. If the battery died, if the USB cable detached, or if the update package was subtly corrupted, the operating system was wiped clean with no fallback—the phone was a permanent paperweight!
  <br /><br />
  <strong>The Seamless A/B Solution (Android 7.0+):</strong> Google duplicated all boot-critical partitions into two mirrored slots: <strong>Slot A and Slot B</strong> (e.g. <code>boot_a</code>/<code>boot_b</code>, <code>system_a</code>/<code>system_b</code>).
  <br /><br />
  When an update arrives, Android installs it in the background to the <em>inactive slot</em> while you continue using apps on the active slot. When you reboot, the bootloader switches slots. If the new slot fails to boot 3 times, the hardware bootloader automatically reverts to the previous working slot! Bricking customer devices became virtually impossible.
</DidYouKnow>

## 3. Dissecting the Partition Layout

A modern Android device partitions its UFS flash storage into **physical boot partitions** and **dynamic logical partitions**:

|                                                                                 |
|  +------------------------+  +------------------------+  +-------------------+  |
|  |       boot_a / _b      |  |     init_boot_a / _b   |  | vendor_boot_a /_b |  |
|  |  (GKI Generic Kernel)  |  |   (Generic Ramdisk)    |  |  (Vendor Modules) |  |
|  +------------------------+  +------------------------+  +-------------------+  |
|                                                                                 |
|  +------------------------+  +------------------------+  +-------------------+  |
|  |      dtbo_a / _b       |  |      vbmeta_a / _b     |  |   userdata (Ext4) |  |
|  |  (Device Tree Overlays)|  | (Crypto Root of Trust) |  |   (Wiped on Unlock|  |
|  +------------------------+  +------------------------+  +-------------------+  |
|                                                                                 |
|  +---------------------------------------------------------------------------+  |
|  |                       super Partition (Physical)                          |  |
|  |  +---------------------+  +---------------------+  +--------------------+ |  |
|  |  |   system_a / _b     |  |   vendor_a / _b     |  |   product_a / _b   | |  |
|  |  | (Generic OS Image)  |  | (Hardware HAL Daemons| | (OEM Customizations)| |  |

## 4. The A/B Slot State Machine

Android uses the `boot_control` HAL to manage slot switching. Each slot has three metadata flags:
1. **Active:** Which slot the bootloader will attempt to load on next restart.
2. **Bootable:** Has an update been written to this slot?
3. **Successful:** Has the OS booted all the way to `PHASE_BOOT_COMPLETED` without crashing?

<DeepDive title="What Happens During an OTA or Wrong-Slot Flash?">
1. **Background Update:** The Android OS is running on Slot `_a`. An OTA update downloads and writes new images into `system_b`, `vendor_b`, and `boot_b`.
2. **Marking Active:** The OS marks Slot `_b` as `Active` and `Bootable` with `tries_remaining = 3`.
3. **Reboot:** The device reboots. The bootloader inspects the metadata and attempts to boot Slot `_b`.
4. **Validation:** If the kernel boots and `system_server` completes startup, `system_server` calls `boot_control->markBootSuccessful()`. Slot `_b` is now officially `Successful`.
5. **Rollback Safety:** If Slot `_b` encounters a kernel panic or bootloop, the watchdog hardware reboots the phone. Each failed boot decrements `tries_remaining`. When `tries_remaining == 0`, the bootloader automatically sets Slot `_a` back as `Active`. The phone boots back to its previous working OS within seconds!
</DeepDive>
