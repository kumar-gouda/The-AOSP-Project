:::danger Irreversible Hardware Risk: Read Before Flashing
Unlocking the bootloader **permanently wipes all data on the device**. Flashing mismatched images or improperly relocking the bootloader can cause a permanent, unrecoverable **hard brick**. Use **only a secondary/dedicated development device**. If you do not have hardware, complete Phase 11 and proceed directly to Phase 13 — the architectural concepts are identical.
:::

<DidYouKnow title="Why Pure AOSP Cannot Boot on Physical Hardware Without Vendor Blobs">
  If Android is open-source (AOSP), why can't you just compile the source tree and flash it directly to a Google Pixel phone?
  <br /><br />
  <strong>The Proprietary Hardware Silicon Reality:</strong>
  While Google open-sources the entire operating system, underlying hardware silicon—such as the GPU (Arm Mali / Qualcomm Adreno), cellular baseband modem, Wi-Fi/Bluetooth chipsets (Broadcom), and camera Image Signal Processor (ISP)—contain proprietary firmware, closed-source drivers, and algorithms protected by non-disclosure agreements (NDAs).
  <br /><br />
  Google distributes these closed-source libraries as pre-compiled <strong>vendor binaries</strong> (blobs) at <code>developers.google.com/android/drivers</code>.
  <br /><br />
  If you compile an AOSP Pixel target without extracting these blobs, Soong will build system images that lack GPU acceleration, cellular baseband communication, and touchscreen drivers. The phone will boot into a black screen with no radio!
</DidYouKnow>

## 3. Step 1: Locating the Device Tree & Kernel

In AOSP source, device configuration files live under `device/google/<codename>/`:

```
device/google/husky/
├── Android.bp
├── AndroidProducts.mk       <-- Declares lunch target names
├── aosp_husky.mk            <-- Main product makefile inheriting phone-core
├── BoardConfig.mk           <-- Hardware architecture, partition sizes, kernel flags
├── device.mk                <-- Packages, copy files, HAL declarations
├── sepolicy/                <-- Device-specific SELinux policy (.te)
└── vintf/                   <-- Vendor interface compatibility manifests
```

---

## 4. Step 2: Extracting the Vendor Binaries

Because silicon IP cannot be open-sourced, download the vendor binary bundle for your exact Pixel build ID from `developers.google.com/android/drivers`:

```bash
# Extract the vendor binaries into your AOSP workspace
tar -xzf google_devices-husky-*.tgz
./extract-google_devices-husky.sh
```

<WhyItWorked>
The extraction script prompts you to accept the license agreement, then extracts binary blobs (Mali GPU drivers, Qualcomm/Tensor radio firmware, audio calibration profiles) into `vendor/google/` and `vendor/google_devices/husky/`. When you execute the build, Soong copies these into `/vendor` inside `super.img`.
</WhyItWorked>

---

## 5. Step 3: Compiling for Hardware

Source the environment and select your hardware target:

```bash
source build/envsetup.sh

# Lunch target syntax: aosp_<codename>-<build-variant>
lunch aosp_husky-userdebug

# Compile complete factory image set
m -j$(nproc)
```

The output images will be generated under `out/target/product/husky/`.

<DeepDive title="Why fastboot flashall Automatically Enters fastbootd">
Notice line 10 in the test output: `Rebooting into fastbootd...`.
Because `super` is a dynamic partition container, `fastboot flashall` writes the physical boot images (`boot`, `init_boot`, `dtbo`, `vbmeta`) while in the firmware bootloader, and then automatically commands the device to reboot into `fastbootd` (userspace recovery) before flashing `super`. This automated orchestration prevents partition alignment corruption.
</DeepDive>

## 7. Step 5: Cherry-Picking a Change and Reflashing

To prove that you have full mastery over physical hardware bring-up, modify a platform string:

1. Edit `frameworks/base/packages/SettingsLib/res/values/strings.xml`:
   - Change `build_number` format or add a custom build suffix.
2. Recompile only the system image:
   ```bash
   m systemimage
   ```
3. Flash the updated image via userspace fastboot:
   ```bash
   adb reboot fastboot
   fastboot flash system $ANDROID_PRODUCT_OUT/system.img
   fastboot reboot
   ```
4. Verify your change in **Settings $\rightarrow$ About Phone $\rightarrow$ Build Number**!
