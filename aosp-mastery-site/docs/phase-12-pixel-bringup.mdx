## 1. Why this is elective - and why it matters

Phases −1 to 11 run entirely on Cuttlefish, where the vendor layer is open and
the boot chain is virtual. A Pixel has **signed vendor blobs** and a **real
bootloader**, so it teaches the last mile: real vendor binaries, real fastboot,
real Verified Boot. That last mile is worth it only if you accept the risk.

<WhyItWorked>
The architecture does not change on hardware; the *consequences* do. On
Cuttlefish a mistake costs a reboot; on a Pixel it can cost the device. This
phase is master-tier precisely because it requires care, a spare device, and
patience - not because the concepts are new.
</WhyItWorked>

## 2. Locate the device tree and kernel sources

For a supported Pixel, both the device tree and the kernel sources are public.
You are *locating and reading*, not authoring, them.

```text
# the device-specific AOSP source directory (community slang "device tree")
device/google/<codename>/          # e.g. device/google/husky for Pixel 8 Pro
# plus a kernel source tree for the device's kernel branch (ACK/GKI)
```

<DoThis
  steps={[
    'Pick a supported codename from the published builds (e.g. husky = Pixel 8 Pro).',
    'Locate device/google/<codename>/ in your checked-out tree.',
    'Locate the kernel sources / prebuilt kernel for that device.',
    'Read the device.mk / BoardConfig to see what the lunch target builds.',
  ]}
/>

## 3. Extract the vendor binaries

The vendor layer is not in AOSP - it comes as **signed binaries** you must
download and extract into your tree. This is the step that makes a Pixel target
whole.

<TestRunner
  title="Download and extract vendor binaries"
  cmd={`# from the device's downloads page (do not guess URLs)
# 1) download the vendor binaries zip for your build + device, and the matching
#    factory image zip (for the extract script)
# 2) from your AOSP root:
unzip ~/Downloads/google_devices-<codename>-<build>-factory-*.zip
# 3) run the extract script it contains (it copies vendor/* into your tree)
./extract-google_devices-<codename>.sh`}
  expect={`... extracting ...
... vendor/... copied into your AOSP tree ...
...

(The extract script places signed vendor binaries where the build expects them.
You are assembling the real vendor layer AOSP does not ship.)`}
/>

## 4. Build with a Pixel lunch target

Now the device participates in the build like any other target.

<TestRunner
  title="Build a Pixel image"
  cmd={`source build/envsetup.sh
lunch aosp_<codename>-userdebug      # e.g. aosp_husky-userdebug
m`}
  expect={`... building ...
... out/target/product/<codename>/ ... images ...

(The device tree + vendor binaries make a complete, flashable image set for a
real Pixel.)`}
/>

## 5. Unlock, flash, boot

The irreversible steps. Unlocking wipes the device; flashing writes images. Do
this only on a spare device.

<TestRunner
  title="Unlock the bootloader"
  cmd={`# put the device in fastboot mode (hold the key combo / adb reboot bootloader)
fastboot devices
fastboot flashing unlock
# confirm on the device screen (this WIPES ALL DATA)`}
  expect={`... <serial>  fastboot ...
... OKAY [ ... ] ...
... (device wipes and reboots) ...

(Unlock wipes userdata - that is the semantics you learned in Phase 11. The
bootloader is now unlocked.)`}
/>

<TestRunner
  title="Flash the full image set and boot"
  cmd={`# from your tree root, with the build complete:
fastboot flashall -w`}
  expect={`... flashing boot_a ...
... flashing boot_b ...
... flashing vbmeta_a ...
... flashing super ...
... finished. total time: ... 
...

(-w wipes userdata first. flashall writes a consistent image set to the slots,
so Verified Boot is satisfied. The device boots your build.)`}
/>

<WhyItWorked>
`flashall` writes a **mutually consistent** set of images (Phase 11's wrong-slot
lesson: the active slot's images and its vbmeta must agree). `-w` wipes userdata
to avoid a mismatched, encrypted-data boot. Because every image comes from the
*same* build, Verified Boot is satisfied and the device boots.
</WhyItWorked>

<Checkpoint
  quiz={{
    question: 'Why does `fastboot flashall -w` work where flashing one image to the wrong slot does not?',
    options: [
      'It disables Verified Boot.',
      'It writes a consistent image set across the slots, so the active slot\'s images and its vbmeta agree - which is exactly the consistency Verified Boot checks.',
      'It uses different hardware.',
      'It ignores the slots entirely.',
    ],
    answer: 1,
    explain:
      'flashall writes a matching set (boot + vbmeta + super, per slot). Consistency across images and vbmeta is what Verified Boot requires; a lone mismatched image fails it.',
  }}
/>

## 6. Cherry-pick a change and reflash

The proof that this is *your* build: make a visible change, rebuild, reflash,

## Break It

<BreakIt
  items={[
    'Symptom: fastboot refuses with "not allowed in locked state." Cause: the bootloader is still locked. Fix: fastboot flashing unlock - but know it wipes all data first.',
    'Symptom: the device bootloops after flashing a single image. Cause: that image does not match the active slot\'s vbmeta (Verified Boot refusal). Fix: flash a consistent set (flashall) rather than a lone image.',
    'Symptom: the device will not boot the new userdata. Cause: old encrypted userdata from a different build. Fix: use -w to wipe userdata, or fastboot -w, accepting the data loss (this is why you use a spare device).',
  ]}
/>

## 7. Mastery check

The bar: **a self-built image boots on your own Pixel**. Concretely, you have:

- Located `device/google/<codename>` and the kernel sources (section 2).
- Extracted the vendor binaries into your tree (section 3).
- Built with the Pixel `lunch` target (section 4).
- Unlocked and flashed a consistent image set, and booted it (section 5).
- Cherry-picked a change, rebuilt, and reflashed it (section 6).

:::caution Risk, documented
The competency map records this phase's testing as **"not-yet (hardware
bring-up; risks documented)."** There is no automated test for "it boots on my
Pixel" - the risk and the reward are both yours, on a spare device.
:::

4.8). This is the artifact the competency map records for this phase.
