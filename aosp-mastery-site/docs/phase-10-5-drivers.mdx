## 1. From module to driver

A module is code the kernel loads. A **driver** is a module that binds to a
device through a **bus**, gets told about that device by **`probe`**, and serves
userspace through a defined interface. The kernel's driver model makes the match
declarative: you describe *what you support*, the kernel calls you when it sees
it.

| Concept | Role |
|---------|------|
| **Bus** | An enumeration mechanism (platform, I2C, SPI, PCI...). |
| **Device tree** | A description of hardware; a driver matches against DT nodes. |
| **`probe`** | Your driver's callback when the kernel matches it to a device. |
| **Char device** | A `/dev` node with `read`/`write`/`ioctl`/`poll`. |
| **IIO** | Industrial I/O subsystem - the standard home for sensors. |

<WhyItWorked>
By matching through the device tree instead of hard-coded addresses, the same
driver works across boards: the DT says "there is a foo at this address", and
your `probe` runs when the kernel sees a `compatible` it supports. This is the
mechanism every real device driver ships with.
</WhyItWorked>

## 2. A device-tree binding and a matching probe

The binding is a contract between the DT author and the driver. Your driver
declares the `compatible` strings it handles; the DT node provides one.

```text
// foo-driver example: a device-tree node
foo@1000 {
    compatible = "acme,foo";
    reg = <0x1000 0x100>;
    status = "okay";
};
```

```c
// foo_driver.c (excerpt) - match a DT compatible and probe
static const struct of_device_id foo_of_match[] = {
    { .compatible = "acme,foo" },
    { /* sentinel */ }
};
MODULE_DEVICE_TABLE(of, foo_of_match);

static int foo_probe(struct platform_device *pdev) {
    // Map registers, set up the char device, etc.
    pr_info("foo: probed\n");
    return 0;
}

static struct platform_driver foo_driver = {
    .probe = foo_probe,
    .driver = {
        .name = "foo",
        .of_match_table = foo_of_match,
    },
};
module_platform_driver(foo_driver);
```

<WhyItWorked>
The kernel's platform bus parsed the DT, found a node with `compatible =
"acme,foo"`, matched it against your `of_match_table`, and called `foo_probe`.
You did not search for the device in code - you described it, and the kernel
delivered it. That is the whole point of the driver model.
</WhyItWorked>

## 3. The file-operations surface: read/write/ioctl/poll

A char device is defined by its `file_operations`. Each entry is a userspace
entry point the kernel routes to your driver.

```c
// foo_fops.c (excerpt)
static ssize_t foo_read(struct file *f, char __user *buf, size_t n, loff_t *off) {
    // copy_to_user your data
    return 0;
}
static ssize_t foo_write(struct file *f, const char __user *buf, size_t n, loff_t *off) {
    // copy_from_user into your buffer
    return n;
}
static long foo_ioctl(struct file *f, unsigned int cmd, unsigned long arg) {
    // handle a control command
    return 0;
}
static __poll_t foo_poll(struct file *f, struct poll_table_struct *pt) {
    // report readiness
    return EPOLLIN | EPOLLOUT;
}
static const struct file_operations foo_fops = {
    .owner = THIS_MODULE,
    .read = foo_read,
    .write = foo_write,
    .unlocked_ioctl = foo_ioctl,
    .poll = foo_poll,
};
```

:::tip IIO instead of a raw char device
For sensors, prefer the **IIO** subsystem over a bespoke char device: it gives
you standard `sysfs`/`/dev/iio:deviceX` interfaces, buffers, and triggers for
free. A char device is the right choice when the interface is genuinely custom;
IIO is the right choice for anything that reads a sensor.
:::

## 4. Test it: kselftest and KUnit

Kernel code is tested **inside the kernel build**. Two frameworks:

- **KUnit** - in-kernel unit tests. You write tests in C, register them, and the
  kernel runs them (often with a `kunit` wrapper in userland output).
- **kselftest** - kernel self-tests driven from userspace, a large suite under
  `tools/testing/selftests/`.

```c
// foo_test.c (excerpt) - a KUnit test of a driver helper
#include <kunit/test.h>

static void foo_adds_up(struct kunit *test) {
    KUNIT_EXPECT_EQ(test, foo_helper(2, 3), 5);
}

static struct kunit_case foo_cases[] = {
    KUNIT_CASE(foo_adds_up),
    {}
};
static struct kunit_suite foo_suite = {
    .name = "foo",
    .test_cases = foo_cases,
};
kunit_test_suite(foo_suite);
```

  title="Run the kernel tests"

./tools/testing/kunit/kunit.py run --kunitconfig=... 
# kselftest: run a self-test
make -C tools/testing/selftests TARGETS=foo run_tests`}
  expect={`... KTAP version 1 ...

...
... kselftest: [PASS] ...

(KUnit reports TAP-style results ("ok 1 ..."); kselftest runs the userspace-driven

/>

<WhyItWorked>
A driver that "seems to work" is not enough. KUnit proves the logic inside the
kernel; kselftest proves the behaviour from userspace. Together they are the
kernel's own testing story - and a passing test is the mastery bar for this
phase.
</WhyItWorked>

## 6. Mastery check

The bar: a driver **bound via device tree, observable from userspace, covered by
a passing kernel test**. Concretely, you have:

- A char/IIO driver with `read`/`write`/`ioctl`/`poll` (sections 2-3).
- A device-tree binding whose `compatible` matches your `probe` (section 2).
- A userspace-observable effect through the char device (section 3).
- **kselftest and a KUnit test** passing (section 4).
- A patched real subsystem, rebuilt GKI, and a successful boot (section 5).

**Spine artifact:** commit the driver, the DT binding, and the test evidence
under `spine/10.5-driver` in your Project Spine fork (plan section 4.8). This is
the artifact the competency map records for this phase.
